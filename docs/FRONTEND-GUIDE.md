# Frontend Guide (`apps/tenant-web`, plus super-admin notes)

Next.js 15 App Router, Tailwind, shadcn-style components, Redux Toolkit + redux-persist, TanStack Query, axios.

## State rules (strict, established conventions)

- **TanStack Query owns ALL server state.** Redux holds only UI/session state. Never mirror API data into Redux.
- Redux slices (`src/store/index.ts`): `auth` (persisted; user + permissions + tokens), `navigation` + `branch` (persisted), `ui`, and **read-only mirrors** `theme` (of next-themes) and `tenant` (of server-resolved TenantProvider) — mirrors are NOT persisted on purpose (single source of truth lives elsewhere; sync bridges: `theme-store-sync.tsx`, `tenant-store-sync.tsx`).
- **Do not call mutations from mount effects via TanStack `useMutation`** — under React 19 StrictMode the observer can stay `pending` forever (bug proven & fixed in onboarding success-step). For fire-on-mount calls use a direct service call + local `useState` machine + `useRef` once-guard (see `features/onboarding/components/steps/success-step.tsx`).
- **The header's `currentBranchId` (Redux `branch` slice, via `useCurrentBranch()`) is the single source of truth for "what branch am I looking at" — any new page/query that should be branch-scoped must read it explicitly and pass it to its data hook(s).** It is NOT auto-attached to requests. As of Prompt 24, `useKpis`/`useAttendanceTrends`/`useRevenueTrends`/`useNewMemberGrowth`/`useRecentActivities` (dashboard), `useMemberList` (`/members`), `useStaffList` (`/staff`), and `useUsers` (`/users`, the IAM "Staff & Access" page — a distinct module from `/staff`, easy to miss) all consume it directly; Attendance (dashboard + history) and Analytics keep their own page-local branch dropdown (needed for an explicit "all branches" option) but seed/re-sync it from `currentBranchId` via a `useEffect` rather than defaulting to "all branches" on every visit. As of Prompt 26, `useMembershipPlanList` (`/memberships` — this one required a real backend addition, `branchId` didn't exist on `listMembershipPlansQuerySchema` at all before this) and `usePaymentList`/`useInvoiceList`/`useIncomeList`/`useExpenseList`/`useFinanceDashboard` (`/payments` `/invoices` `/income` `/expenses`) also consume it directly. If you add a new branch-scoped list/widget, follow the same pattern — don't assume the header selector does anything on its own, and don't assume the backend already accepts `branchId` either (check the query schema, not just the frontend type).
- **Error messages**: `toAuthServiceError` (`features/auth/services/api-client.ts`) is the ONE place every feature's `toXError` wrapper (`toMemberError`/`toStaffError`/`toIamError`/etc.) funnels through. As of Prompt 26 it builds its message from the backend's per-field `errors[]` (`{field, message}`) when present — e.g. "Validity End: Validity start date must be on or before the validity end date" — falling back to the generic top-level `message` otherwise. Don't hand-roll error-message extraction in a new feature's `toXError` — it already gets field-level detail for free from this shared function.

## Provider stack (`src/providers/app-providers.tsx`)

Redux → PersistGate → QueryClient → ThemeProvider(+ThemeStoreSync) → TenantProvider(+TenantStoreSync) → AuthProvider → RealtimeProvider → chrome (TopProgressBar, SessionExpiryModal, Toaster).

## Multi-tenancy on the client

- `src/middleware.ts` extracts slug from Host (`{slug}.localhost:3001` / `{slug}.<domain>`), `?tenant=` override, or cookie → header `x-tenant-slug`.
- Root layout resolves tenant server-side (`features/tenant/resolve.ts` → `GET /public/tenants/resolve`) and paints branding CSS vars on `<body>` (`--primary`, `--tenant-secondary`). Unknown slug → `PLATFORM_TENANT` fallback; `/login` then renders `FindGymForm` instead of a dead login form.
- `apiClient` (`features/auth/services/api-client.ts`): attaches `X-Tenant-Slug` + Bearer, dedupes identical in-flight requests (AbortController), 401→refresh-once-and-retry, tenant-wide error redirects (suspended/expired/maintenance), dispatches request start/finish for the top progress bar.

**Gym Settings patterns (P12)**:
- Image uploads share one util, `lib/image-to-data-url.ts` → `fileToDataUrl(file, maxDimension, quality?)` (canvas downscale → JPEG data-URL) — extracted from the P11 avatar-upload component, which now imports it too rather than duplicating the logic. No object storage exists; "public URL" = the data-URL itself, stored inline.
- Every branding page mutation calls `router.refresh()` afterward (`refreshPortalChrome()` in `branding/page.tsx`) — since the backend invalidates the tenant resolve cache on write, this re-renders the server-side root layout with fresh branding without a hard reload, which is how the sidebar/login logo & colors update live.
- All 4 pages (`profile`/`business`/`branding`/`invoice`) follow the same dirty-form shape: local `useState<FormState|null>`, `useEffect` seeds it once from the query, a `baseline` recomputed from the query data for the `isDirty` diff, and the shared `UnsavedChangesBar` for Save/Cancel — copy this shape for any future settings-style page instead of the avatar/profile-form pattern.

**Staff Management patterns (P13)**:
- `components/ui/data-table.tsx`'s `DataTableColumn.header` was widened from `string` to `React.ReactNode` (backward compatible — a plain string is still a valid ReactNode) so the Staff list page could put a sortable-column button and a "select all" checkbox in table headers. Reuse this if a future list page needs the same.
- `components/ui/confirm-dialog.tsx` (new, generic `ConfirmDialog`) — the first shared "are you sure?" dialog in the UI kit; every destructive/bulk staff action (suspend/deactivate/delete/bulk-*) uses it. Prefer it over a bespoke dialog for any future confirm-before-action need.
- Staff detail page (`(portal)/staff/[staffId]/page.tsx`) combines profile+employment fields into ONE form/Save button (backed by the single `PATCH /staff/:id`), but Branch assignment and Role assignment are separate mini-sections each with their own immediate-save button — because those are separate `PUT` endpoints, mirroring how the Users detail page splits Roles/Branches editors from the main profile form.
- The Staff list/detail pages reuse `AvatarUpload` and `UserStatusBadge` directly from the `iam` feature, and `UnsavedChangesBar`/`useUnsavedChangesWarning` directly from `gym-settings` — none of these were copied or reimplemented.

**Member Management patterns (P14)**:
- `lib/image-to-data-url.ts` gained a second export, `fileToRawDataUrl(file, maxBytes)` — the Document Management upload field needs to accept PDFs, and a PDF can't go through `createImageBitmap`/canvas like `fileToDataUrl` does. `document-upload.tsx` picks between the two based on `file.type.startsWith('image/')`.
- Member detail page (`(portal)/members/[memberId]/page.tsx`) follows the same "one big form + separate mini-sections" split as Staff: profile/medical/address/notes are one `PATCH /members/:id` form with `UnsavedChangesBar`; Branch and Trainer are separate immediate-save mini-sections (`PUT` endpoints); Membership assign/renew/upgrade/freeze/unfreeze are inline action buttons with no dirty-state tracking (each click is its own mutation, matching how the backend models them as distinct lifecycle transitions, not editable fields).
- `trainer-select.tsx` importing `useStaffList` from the `staff` feature (not duplicating a members-local trainer query) is the clearest cross-module reuse example in the codebase so far — copy this pattern (import the other feature's hook directly) before adding a parallel query for data another feature's module already owns.

## Global Loading & Performance Optimization patterns (Prompt 23)

An app-wide UX/infra pass — no business logic touched. Read this section before adding a new loading state, list page, or button anywhere in the app; almost everything below is a shared primitive meant to be reused, not a one-off.

- **`useDelayedLoading(isLoading, {showDelayMs, minDurationMs})`** (`src/hooks/use-delayed-loading.ts`) is the anti-flicker primitive behind every loader in the app, including the top progress bar. A `showDelayMs` window (default 150ms) swallows near-instant operations entirely — most cached/fast requests never visibly flash a spinner. A `minDurationMs` floor (default 300ms) once shown means it can never blink in and immediately back out. Reach for this before building a new "is this thing loading" conditional — don't gate a spinner directly on a raw `isPending` boolean if it can plausibly resolve in well under 150ms.
- **Navigation loading**: `TopProgressBar` (`src/components/top-progress-bar.tsx`) is fed by two independent Redux signals — `ui-slice.pendingRequests` (pre-existing, driven by the axios client's interceptors) and `ui-slice.navigationPending` (new — `NavigationProgressProvider`, `src/components/navigation-progress-provider.tsx`, mounted once in `app-providers.tsx` wrapped in `<Suspense>` since it uses `useSearchParams`). The provider patches `window.history.pushState`/`replaceState` **once at the module level** (a `historyPatched` guard prevents re-patching, e.g. across Fast Refresh) plus a `popstate` listener — this is how the Next.js App Router performs a client-side navigation under the hood, so it catches every trigger the spec lists (sidebar, header menu, breadcrumb, tabs, internal `<Link>`s, browser back/forward) without instrumenting each one individually. **Gotcha found live**: dispatching the Redux action directly inside the patched `pushState`/`replaceState` call caused a real `useInsertionEffect must not schedule updates` console error — the App Router itself sometimes calls `pushState` from `useInsertionEffect`-timed internals, where React forbids scheduling updates. Fixed by wrapping the dispatch in `queueMicrotask()`. If you ever patch a browser API that the framework itself might call from a similarly-timed internal, defer your side effect the same way rather than assuming a plain `dispatch()` is safe.
- **Initial load**: `InitialLoadOverlay` (`src/components/initial-load-overlay.tsx`) is rendered as a **sibling of `AppProviders`**, directly in `app/layout.tsx` — not nested inside it — specifically so it needs no store/query-client/tenant context to exist. It's present in the very first server-rendered HTML (client components still render server-side for the initial response) and fades itself out via a plain `useEffect`, no earlier than a short minimum-visible floor.
- **Button loading state**: `LoadingButton` (`src/components/ui/loading-button.tsx` — promoted here from `features/auth/components/` in this prompt, 18 import sites repointed with zero behavior change) is now the standard for every action button, superseding the older `disabled={mutation.isPending}` + manual text-swap convention (still functionally fine, but no spinner). Two shared components were converted for maximum leverage rather than touching every page individually: `UnsavedChangesBar`'s Save button (used by every "one big form" detail/edit page — Members/Staff/Branches/Membership Plans/Workout Plans/Diet Plans/all 4 Gym Settings pages) and `ConfirmDialog`'s Confirm button (used by every delete/activate/deactivate/restore/bulk-action confirmation app-wide, ~20 call sites). New pages should use `LoadingButton` directly rather than the old text-swap pattern.
- **Form submission**: `useSubmitHandler(action)` (`src/hooks/use-submit-handler.ts`) is for forms that don't already go through a TanStack `useMutation` (which gives `isPending` for free) — it adds a `ref`-based guard against a duplicate concurrent submit even in the render-frame window before a disabled button visually stops accepting clicks, plus centralized error-to-message normalization. `action` is read from a ref on every call, so passing a fresh inline closure each render (the common case — it closes over current form state) is safe, never stale. Used by the Contact Sales/Billing dialog and both Staff/Users CSV Export buttons (which previously had zero loading feedback at all — a real, not just cosmetic, gap). Don't reach for it if a `useMutation` already exists for the action; that already covers 95% of the same need.
- **Table loading**: `DataTable` (`src/components/ui/data-table.tsx`) gained `error`/`onRetry` props — pass a query's `.error` and `.refetch` straight through. Previously a failed query had no distinct rendering path and silently fell through to the empty state; now it shows a dedicated error state (reusing `EmptyState`'s shape with a destructive-tinted icon) with a Retry button. Applied to all 17 pages using `DataTable` as of this prompt — add it to any new one too. The inline skeleton was extracted into a standalone `TableSkeleton` (`src/components/ui/table-skeleton.tsx`), reusable outside `DataTable` for any other table-shaped view.
- **New loader components**: `FullScreenLoader`, `PageLoader`, `SectionLoader`, `CardSkeleton`, `FormSkeleton` (`src/components/ui/`) — three loader tiers (full-screen > page > section) plus two more skeleton shapes, alongside the pre-existing `Skeleton`/`Spinner`/`TableSkeleton`. None of them build in `useDelayedLoading` themselves — that's a composition decision left to the call site (`if (useDelayedLoading(query.isPending)) return <PageLoader />`), keeping the loader components themselves simple/pure.
- **Debounced search**: `useDebouncedValue` (`src/hooks/use-debounced-value.ts` — promoted here from `features/onboarding/hooks/`, its only prior consumer) is now applied to all 14 list pages with a live search box. The pattern: keep the raw `search` state for the controlled input (typing feels instant), but pass `useDebouncedValue(search, 300)` into the query hook's params instead of `search` directly — `setPage(1)` still fires eagerly on every keystroke (harmless/idempotent), only the actual refetch is debounced. The Notification History page's search is deliberately NOT debounced — it's a pure client-side array `.filter()` over already-fetched data, no network round-trip, so debouncing would only add latency for no benefit. Don't debounce a client-side filter.
- **Data caching**: per-hook `staleTime` overrides (not a global default change) for the spec's named "frequently accessed" list — Dashboard/Staff-list/Members-list/Membership-Plans-list at 1 minute, Branches'/Membership-Plans' `assignable` endpoints and all 6 Gym Settings queries at 5 minutes. User Profile needs no query-level caching at all — it's sourced from Redux (+ redux-persist), not TanStack Query, so it's already cached for the whole session. Every mutation's existing `invalidateQueries` call is untouched and still forces an immediate refetch after a real change — don't add a `staleTime` to a query whose data changes on a sub-minute cadence without checking its invalidation story first.
- **Code splitting**: `next/dynamic` with `ssr:false` applied to the camera-based QR Scanner (`attendance/check-in`) and the Recharts-heavy dashboard `ChartsGrid` — both good candidates (a scanner that needs `getUserMedia`, and a large charting library not needed on most other routes). Most other routes don't need this — Next.js App Router already code-splits per-route automatically; only reach for `next/dynamic` for a genuinely heavy, conditionally-needed, or browser-only component within a page that also has a fast path not needing it.
- **Virtualization**: new `@tanstack/react-virtual` dependency backs a generic `VirtualizedList` (`src/components/ui/virtualized-list.tsx`, for a flat item list) plus direct `useVirtualizer` usage inside the Permission Matrix's `<tbody>` (`app/(portal)/permissions/page.tsx`) via the "two spacer `<tr>`s" technique — real `<table>`/`<tbody>`/`<tr>` semantics stay intact (no `display: grid` override needed), only the rows in/near the viewport are ever mounted. This was the **one** place in the app with a genuinely large, unpaginated, client-rendered list (100+ permission keys × every role column); every other list already paginates server-side (20/page), which remains the correct fix for "large datasets" — don't reach for virtualization where pagination already solves the problem.
- **`next.config.mjs`** gained `experimental.optimizePackageImports: ['lucide-react', 'recharts']` — tree-shakes both large barrel-file libraries (used on nearly every page) automatically, no code changes needed at call sites.
- **Memoization**: `StatisticCard` (rendered many times per KPI grid, typically with primitive/stable props) wrapped in `React.memo`. Not applied to `DataTable` itself — its `columns`/`rows` props are recreated fresh on every parent render in every current call site, so memoizing the table without also `useMemo`-ing every page's `columns` array wouldn't have actually prevented re-renders; that would be a much larger, separate change.

The login rate limiter (`rl:login:{tenantId}:{email}`, 10/15min, Redis-backed — see BACKEND-GUIDE.md) is easy to exhaust when iterating on a two-tab or repeatedly-retried test script; if `/auth/login` starts 429-ing mid-session, `docker exec gym-saas-redis redis-cli DEL "rl:login:{tenantId}:{email}"` unblocks local testing immediately (safe — it's your own dev Redis, not a security bypass of anything external). Also watch for the test tenant's OWN subscription lapsing across a long session — `prompt10test` was provisioned as a TRIAL long ago and a BullMQ sweep (see BACKEND-GUIDE.md §Billing) flips both `tenants.status` and `subscriptions.status` to `SUSPENDED` once `trial_ends_at`/`current_period_end` pass; login then fails with `TENANT_SUSPENDED` even with correct credentials. Fix by extending both date columns and setting both status columns back via SQL, then flushing the `tenant:slug:*` Redis cache key (found live during Prompt 17).

**Gotcha confirmed again in P14**: `next build` while `next dev` still holds the port corrupts `.next` — always `Stop-Process` the dev server (check `Get-NetTCPConnection -LocalPort 3001`) before a production build, then restart dev afterward. Also seen: `next build`'s "Collecting page data" step can spuriously fail with `Cannot find module for page: /some-unrelated-page` on Windows — a transient file-system race, not a real error; retrying the same build (no code changes) succeeds. Don't chase it as a bug if `tsc --noEmit` and `eslint` are both clean.

**Gotcha seen in P15**: a `ConfirmDialog`-driven status action (Activate/Deactivate) on a page reached IMMEDIATELY after another mutation (e.g. right after Duplicate navigates to the new plan's detail page) can flake in Playwright with "element was detached from the DOM, retrying" on the Confirm button — plausibly a React Strict Mode double-render/query-refetch race in dev, not a real bug (the exact same action worked fine seconds earlier on a page that had been settled longer). Fix in the test, not the app: add a short `waitForTimeout` (300-500ms) after the button that opens the dialog appears, before clicking it, and again before clicking Confirm.
