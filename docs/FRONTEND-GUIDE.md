# Frontend Guide (`apps/tenant-web`, plus super-admin notes)

Next.js 15 App Router, Tailwind, shadcn-style components, Redux Toolkit + redux-persist, TanStack Query, axios.

## State rules (strict, established conventions)

- **TanStack Query owns ALL server state.** Redux holds only UI/session state. Never mirror API data into Redux.
- Redux slices (`src/store/index.ts`): `auth` (persisted; user + permissions + tokens), `navigation` + `branch` (persisted), `ui`, and **read-only mirrors** `theme` (of next-themes) and `tenant` (of server-resolved TenantProvider) — mirrors are NOT persisted on purpose (single source of truth lives elsewhere; sync bridges: `theme-store-sync.tsx`, `tenant-store-sync.tsx`).
- **Do not call mutations from mount effects via TanStack `useMutation`** — under React 19 StrictMode the observer can stay `pending` forever (bug proven & fixed in onboarding success-step). For fire-on-mount calls use a direct service call + local `useState` machine + `useRef` once-guard (see `features/onboarding/components/steps/success-step.tsx`).
- **The header's `currentBranchId` (Redux `branch` slice, via `useCurrentBranch()`) is the single source of truth for "what branch am I looking at" — any new page/query that should be branch-scoped must read it explicitly and pass it to its data hook(s).** It is NOT auto-attached to requests. As of Prompt 24, `useKpis`/`useAttendanceTrends`/`useRevenueTrends`/`useNewMemberGrowth`/`useRecentActivities` (dashboard), `useMemberList` (`/members`), `useStaffList` (`/staff`), and `useUsers` (`/users`, the IAM "Staff & Access" page — a distinct module from `/staff`, easy to miss) all consume it directly; Attendance (dashboard + history) and Analytics keep their own page-local branch dropdown (needed for an explicit "all branches" option) but seed/re-sync it from `currentBranchId` via a `useEffect` rather than defaulting to "all branches" on every visit. As of Prompt 26, `useMembershipPlanList` (`/memberships` — this one required a real backend addition, `branchId` didn't exist on `listMembershipPlansQuerySchema` at all before this) and `usePaymentList`/`useInvoiceList`/`useIncomeList`/`useExpenseList`/`useFinanceDashboard` (`/payments` `/invoices` `/income` `/expenses`) also consume it directly. If you add a new branch-scoped list/widget, follow the same pattern — don't assume the header selector does anything on its own, and don't assume the backend already accepts `branchId` either (check the query schema, not just the frontend type).
- **Error messages**: `toAuthServiceError` (`features/auth/services/api-client.ts`) is the ONE place every feature's `toXError` wrapper (`toMemberError`/`toStaffError`/`toIamError`/etc.) funnels through. As of Prompt 26 it builds its message from the backend's per-field `errors[]` (`{field, message}`) when present — e.g. "Validity End: Validity start date must be on or before the validity end date" — falling back to the generic top-level `message` otherwise. Don't hand-roll error-message extraction in a new feature's `toXError` — it already gets field-level detail for free from this shared function.

## Accessibility & RUM (Prompt 38)

- **`eslint-plugin-jsx-a11y`** (`plugin:jsx-a11y/recommended`) is enabled in both apps' `.eslintrc.json`, on top of whatever subset `next/core-web-vitals` already bundled. `label-has-associated-control` is configured with `controlComponents: ["Checkbox"]` — a native `<label>` wrapping the custom `Checkbox` (Radix, renders a labelable `<button>`) is the established, correct pattern for checkbox rows; don't restructure it if the rule flags a *new* one, just confirm it's the same shape and it'll already be covered. A few genuine false positives are suppressed inline with a comment explaining why (`heading-has-content` on `AlertTitle`/`CardTitle` — content arrives via spread `...props`, the rule can't see through that; `anchor-has-content` on the AI chat's markdown-renderer `a` override, same reason; `aria-role` on `<MessageBubble role="ASSISTANT">` — that `role` is the component's own sender-type prop, not a DOM ARIA role) — if a NEW violation looks like one of these shapes, it probably is; if it's a genuinely unlabeled interactive element, fix it for real (see `holidays-editor.tsx`'s delete button or `search-bar.tsx`'s placeholder-as-aria-label default for the pattern).
- **`e2e/` (repo root)**: `playwright.config.ts` + `a11y.spec.ts` — real axe-core scans (`@axe-core/playwright`) against both apps' `/login` pages, asserting zero serious/critical WCAG 2 A/AA violations. Run locally with `pnpm test:a11y` against your own running dev stack (same pattern as every other live-verification this project does). Wired into CI as a new `a11y` job that stands up the full stack from scratch in the runner — see that job's own comment in `ci.yml` for the one caveat (proven working locally, not yet exercised in a real Actions run).
- **`components/web-vitals-reporter.tsx`** (both apps, mounted once in the root `layout.tsx`, outside `AppProviders`): `next/web-vitals`'s `useReportWebVitals` → `navigator.sendBeacon` → `POST /public/rum`. No vendor lock-in (not Vercel Analytics/Speed Insights) — metrics just land as structured Winston log lines for now (`core/logging/logger.ts`, `event: 'web-vital'`).

## Content-Security-Policy (Prompt 41)

Both `next.config.mjs` files (`apps/tenant-web`, `apps/super-admin`) set a real CSP + `X-Content-Type-Options`/`Referrer-Policy`/`Permissions-Policy` via `async headers()` — neither app had ANY security headers before this. `script-src`/`style-src` are `'self' 'unsafe-inline'` (plus `'unsafe-eval'` in dev only, for Fast Refresh/HMR — a CSP without it breaks `next dev` outright) rather than a nonce-based rollout: tenant-web paints per-tenant branding as an inline `style` ATTRIBUTE on `<body>` (`app/layout.tsx`), and CSP nonces only ever cover `<style>`/`<script>` ELEMENTS, never inline attributes — so `style-src` needs `'unsafe-inline'` regardless, which removes most of the benefit a full nonce rollout would buy. `img-src` allows any `https:` origin (images can't execute script, and every upload is magic-byte-verified server-side as of Prompt 40) instead of requiring exact per-deployment bucket allow-listing.

**If you add a new external origin this app talks to (a new API, a CDN, an analytics beacon, etc.), it needs an explicit `connect-src`/`img-src` entry or the browser silently blocks it** — this is NOT caught by typecheck/lint/build/vitest, only by live testing with the browser console open. This exact class of gap shipped once during this prompt itself: `connect-src 'self' <api-origin>` alone silently blocked every Socket.IO WebSocket connection (`features/realtime/socket-client.ts`, tenant-web only) — a browser's CSP does NOT treat an `http://host` `connect-src` entry as covering a `ws://host` upgrade to the same host, so the http(s) origin and its ws(s) equivalent both need to be listed. Caught only by a real Playwright pass watching `page.on('console')` for CSP violation messages during actual login+navigation — a check that only confirms the header is PRESENT (not that the policy actually works) would have missed this entirely.

## Mandatory Two-Factor Authentication (Prompt 42)

Real TOTP 2FA replaced a dead-end email-OTP-labeled-as-authenticator-app UI (see BACKEND-GUIDE.md §Mandatory Two-Factor Authentication for the backend side — the grace-token pattern, the `TenantSettings.mfaRequiredRoles` policy).

- **Login branches three ways**, not two: `login-form.tsx` now checks `result.kind === 'mfa_setup_required'` (new) alongside the pre-existing `otp_required`/`success`, redirecting to `${AUTH_ROUTES.mfaSetup}?email=…&setupToken=…`. Only `otp_required` dispatches Redux `otpChallengeIssued` — `mfa_setup_required` carries no session yet, so it has no Redux state of its own; the setup-token is passed through the URL and consumed directly by `mfa-setup-form.tsx`.
- **One setup/confirm engine, two UI entry points** — `MfaSetupForm` (full-page, `/mfa-setup`, the forced grace flow) and `EnableTwoFactorDialog` (self-service, `/settings`'s Security tab) both drive the exact same `authService.beginMfaSetup`/`beginTwoFactorSetup` → QR/secret display → code confirm → one-time backup-codes screen sequence, just wired to different begin/confirm service calls. Copy one when building the other rather than diverging.
- **Real bug found + fixed via live Playwright, not by inspection**: both components originally fired their begin-setup call through a TanStack `useMutation` inside a mount/dialog-open `useEffect`. This is the exact anti-pattern already documented above (§State rules: "Do not call mutations from mount effects") and proven once before in `features/onboarding/components/steps/success-step.tsx` — under React 19 StrictMode's double-invoked effects, the mutation observer stayed `pending` forever even though the request itself returned a genuine 200 (confirmed via `page.on('response')` logging: real QR data came back, but the UI just spun). Fixed identically to the onboarding precedent: a local `useState` status machine (`{status:'pending'|'success'|'error'}`) populated by a **direct** `authService.beginMfaSetup()`/`beginTwoFactorSetup()` promise call inside a `useRef`-guarded effect — no `useMutation` in the mount/open-fired path. The user-click-fired `confirm` step is unaffected and stays a normal `useMutation` (`useConfirmMfaSetup`/`useConfirmTwoFactorSetup`) — the anti-pattern is specific to mount/open-effect-fired mutations, not mutations in general. If you add a third begin/setup-style flow that must fire on mount or on a dialog opening, use this same local-state-machine shape from the start rather than reaching for `useMutation`.
- **Backup codes in `otp-form.tsx`**: `OtpInput` is hard-coded to 6 digits; a backup code is 11 characters (`XXXX-XXXXXX`). The "Use a backup code instead" toggle swaps to a plain `<Input>` for that branch rather than trying to stretch `OtpInput` to a variable length.
- **`autoFocus={false}` on `OtpInput` inside dialogs**: `EnableTwoFactorDialog` explicitly passes `autoFocus={false}` to override `OtpInput`'s own default of `true`, since Radix `Dialog` already focus-traps to its own first focusable element — two competing autofocus attempts fight each other. `jsx-a11y/no-autofocus` still flags the mere presence of the prop regardless of value; suppressed with a justified inline comment, same precedent as elsewhere in this codebase.

## Global Search (Prompt 44)

`components/layout/global-search.tsx` (mounted in `header.tsx`) previously only filtered the sidebar nav's own labels client-side — a deliberate stub, per its own prior code comment, until "those modules' data" existed. It now ALSO queries the new `GET /search` endpoint (new `features/search/` — `types/`, `services/search.service.ts`, `hooks/use-search.ts#useGlobalSearch`) and renders grouped results: a "Pages" group (the original instant nav-label filter, untouched) plus "Members"/"Staff"/"Branches" groups from the API. The nav-label filter stays synchronous (no debounce, no network); the API call is debounced 300ms via the existing `useDebouncedValue` hook (`hooks/use-debounced-value.ts`) and only fires once the query is 2+ characters (`useGlobalSearch`'s `enabled` gate) — matches the pre-existing "debounced search input" pattern this codebase already uses elsewhere (e.g. `MemberCheckinSearch`), not a new one invented for this feature. Clicking a result navigates via `router.push(item.url)` (a plain `/members/:id`-style path returned by the API) and clears the query.

**Known verification gap**: no Playwright/browser tool was available in the session this was built — the dropdown's live interaction (type → see grouped results render → click → land on the right page) was verified only via a passing production build/typecheck/lint and a curl-level check of the API response shape, NOT a real browser click-through. Do a real Playwright pass before making further changes here to establish a behavioral baseline first.

## GDPR Export/Erasure for Members (Prompt 46)

Two entry points, same underlying JSON bundle from `GET /members/:id/gdpr-export` (staff) or `GET /portal/gdpr-export` (member self-service):

- **Staff side**: `(portal)/members/[memberId]/page.tsx` gained a "Data & privacy" card — "Export data" (any staff who can view the member; `useGdprExport` in `features/members/hooks/use-members.ts`, calls `member.service.ts#gdprExport` which downloads the response as a `.json` file client-side via a local `downloadJson` helper — the backend returns plain JSON, not a pre-built blob, unlike the CSV/PDF exports elsewhere in this app) and, only when `hasPermission('members:erase-data')`, an "Erase data" button behind the existing `ConfirmDialog` (`destructive`) — same pattern as every other destructive action on this page.
- **Member-portal side**: the dashboard (`app/portal/(authenticated)/dashboard/page.tsx`) gained a "My data" card with a "Download my data" button. Calls `memberPortalService.downloadGdprExport(memberCode)` directly (no TanStack hook) — mirrors the existing `downloadInvoice` call on the Invoices page, which is also called directly rather than through a hook, since a side-effecting file download isn't cacheable query state.
- **No self-service erasure UI exists anywhere** — erasure is staff-only by design (see BACKEND-GUIDE.md §GDPR Export/Erasure for Members for why). Don't add an "Erase my account" button to the member portal without discussing the human-in-the-loop rationale first.

## Multi-tenancy on the client

- `src/middleware.ts` extracts slug from Host (`{slug}.localhost:3001` / `{slug}.<domain>`), `?tenant=` override, or cookie → header `x-tenant-slug`.
- Root layout resolves tenant server-side (`features/tenant/resolve.ts` → `GET /public/tenants/resolve`) and paints branding CSS vars on `<body>` (`--primary`, `--tenant-secondary`). Unknown slug → `PLATFORM_TENANT` fallback; `/login` then renders `FindGymForm` instead of a dead login form.
- `apiClient` (`features/auth/services/api-client.ts`): attaches `X-Tenant-Slug` + Bearer, dedupes identical in-flight requests (AbortController), 401→refresh-once-and-retry, tenant-wide error redirects (suspended/expired/maintenance), dispatches request start/finish for the top progress bar.

## Global Loading & Performance Optimization patterns (Prompt 23)

An app-wide UX/infra pass — no business logic touched. Read this section before adding a new loading state, list page, or button anywhere in the app; almost everything below is a shared primitive meant to be reused, not a one-off.

- **`useDelayedLoading(isLoading, {showDelayMs, minDurationMs, offDelayMs})`** (`src/hooks/use-delayed-loading.ts`) is the anti-flicker primitive behind every loader in the app. A `showDelayMs` window (default 150ms) swallows near-instant operations entirely — most cached/fast requests never visibly flash a spinner. A `minDurationMs` floor (default 300ms) once shown means it can never blink in and immediately back out. `offDelayMs` (default 200ms, Prompt 33) **debounces the "off" transition**: once `isLoading` flips false, the hook waits `offDelayMs` before committing to hide — if `isLoading` flips back to `true` within that window, the hide is cancelled outright (the effect's cleanup clears the pending hide timer) and the loader just stays visible, no flicker. This exists because "loading" is often really a CHAIN of separate signals, not one continuous one — see `GlobalLoader` below for the concrete bug this fixed. Reach for this hook before building a new "is this thing loading" conditional — don't gate a spinner directly on a raw `isPending` boolean if it can plausibly resolve in well under 150ms.
- **The single app-wide loading indicator (Prompt 33)**: split into a container and a presentational component. `GlobalLoader` (`src/components/loading/global-loader.tsx`) owns WHEN it shows — mounted exactly once at the root of `AppProviders`, fed by two Redux signals in `ui-slice.ts` (`pendingRequests`: every in-flight `apiClient` call; `navigationPending`: `NavigationProgressProvider`, mounted alongside it wrapped in `<Suspense>` since it uses `useSearchParams`) — every route and every button that goes through the shared `apiClient` gets it automatically, nothing to import per-page. `GymLoader` (`src/components/loading/gym-loader.tsx`) owns what it looks like — pure presentational, takes `progress`/`label` props only, no store reads: a spring-animated (`framer-motion`) progress ring + a barbell that racks up plates as `progress` climbs, cycling tip text underneath. Edit `global-loader.tsx` to change WHEN the loader shows; edit `gym-loader.tsx` to change what it looks like. No request in this app reports real byte-level progress, so `GlobalLoader` drives `progress` with a cosmetic **asymptotic climb** (fast start, crawls toward a 92% cap while genuinely still pending — never claims 100% before the work is actually done — snaps to 100% the instant loading ends), the same trick NProgress-style bars use for indeterminate loads.
  - This used to be three separate, sometimes-simultaneous loaders — a thin top-of-viewport bar (`TopProgressBar`), a centered pill, and an unrelated spinner from the App Router's `loading.tsx` Suspense boundary (`PageLoader`) — consolidated to just one on user request: `TopProgressBar`/`PageLoader` were deleted, `(portal)/loading.tsx` and `(auth)/loading.tsx` now render `null` (the file must still exist so the App Router treats navigation as non-blocking, it just no longer shows a competing spinner).
  - **A fourth bug, found via user report after the above shipped**: "loader hits 100% and closes, but the page hasn't changed yet." Root cause: a real gap between `navigationPending` clearing (route/pathname committed) and the new page's own first data fetch actually registering in `pendingRequests` — the route's JS chunk still has to load, the component still has to mount, its effect still has to fire the query. Confirmed live via network-log timestamps to run 500-1100ms in `next dev`, not a small/fixed number. During that gap `isLoading` read `false`, so the hide countdown started prematurely. Fixed via `useDelayedLoading`'s new off-debounce (see above); `GlobalLoader` passes `offDelayMs: 900` specifically (wider than the hook's own 200ms default) since the measured real-world gap exceeded that. Verified live: screenshots through a click with the data request delayed 1.5s show the loader staying up (page's own skeleton visible underneath) for the entire wait, reaching "100% ready" only once the real rows have already rendered behind it.
  - **`NavigationProgressProvider` has two independent trigger sources**, both funnelling into the same `notifyStart()`: (1) a capture-phase `click` listener on `document` — the *primary* signal, fires the instant a same-tab internal link is clicked (filters out modifier-key clicks, new-tab, download, external hrefs, hash-only links), and (2) patched `window.history.pushState`/`replaceState` (`historyPatched` module guard, patched once) plus a `popstate` listener, which also catches programmatic `router.push()` calls that don't originate from a click. **Why both exist — a real gap found live via a user-provided DevTools screenshot**: the App Router doesn't call `pushState` until its RSC route-fetch resolves, and in `next dev` the *first* visit to a route triggers on-demand server compilation that can take several real seconds with zero client-side signal until it finishes — a `pushState`-only trigger has no chance to show anything for that whole window. The click listener fires before any of that async work even starts.
  - **The click-listener effect is deliberately NOT gated by the `historyPatched` module guard** (unlike the history-patching itself, which must only ever happen once — re-patching on every remount would stack wrappers). Both effects call through a `notifyStartRef` rather than closing over `notifyStart` directly, so the once-patched `pushState` still always invokes the current version. If you gate a `document`-level listener behind a "set up once, never again" module guard the same way the history patch needs, React Strict Mode's dev-only mount→cleanup→remount dance on initial load removes the listener in the cleanup pass and then skips re-adding it (the second pass hits the module guard's early return) — the listener silently stops working after the very first page load in dev. Give listeners their own effect with the normal mount/unmount lifecycle instead.
  - **A real gap found live via user report (this prompt)**: the pushState patch "catches" a programmatic `router.push()` in the sense that it eventually fires — but only once `pushState` is actually called deep inside the App Router's navigation machinery, which (same as the doc comment above explains) doesn't happen until the RSC fetch has already resolved. For a real `<a href>` click, the click listener papers over this by firing instantly, before any of that async work starts — but a `router.push()` triggered from a plain `<button onClick>`, a `role="link"` card/row, a `DropdownMenuItem` not wrapped in `asChild`+`<Link>`, or a toast action has no anchor for the click listener to attach to, so it fell through to the late-firing pushState path: no loader at all until the navigation had basically already finished (user-reported: "click a button, nothing happens, then the page suddenly changes" — reproduced live in `global-search.tsx`'s search-result buttons, super-admin's `plans` card grid + several "Back to X" buttons, and both apps' AI-assistant error-toast action). **Fix**: `notifyProgrammaticNavigation(targetUrl?)`, exported from `navigation-progress-provider.tsx` (a module-level ref to the current `notifyStart`, set on every render), gives any non-`<Link>` call site the same early, generation-tracked signal a real link click gets — call it immediately before the `router.push()`. Prefer a real `<Link>` (with `asChild` for dropdown items / button-styled links) wherever the destination is static; reach for `notifyProgrammaticNavigation` only when the navigation is genuinely conditional/dynamic (search results, computed redirect targets, post-mutation navigation, toast actions).
  - **Gotcha found live**: dispatching the Redux "started" action directly inside the patched `pushState`/`replaceState` call (or the click listener) caused a real `useInsertionEffect must not schedule updates` console error — the App Router itself sometimes calls `pushState` from `useInsertionEffect`-timed internals, where React forbids scheduling updates. Fixed by wrapping the dispatch in `queueMicrotask()`. That defer then creates its OWN ordering hazard: for an already-resolved/fast navigation, the "route resolved" effect can dispatch `navigationFinished` *before* the deferred `navigationStarted` microtask even runs, which would otherwise leave the flag stuck permanently "on" (confirmed live: `navigationPending: true` for 5.8+ seconds after a nav click that itself completed in 64ms). Fixed with two synchronous refs: `pendingGenRef` (a generation counter — only the latest `notifyStart` call may still dispatch "started") and `pathKeyRef` (kept fresh every render — the deferred microtask checks whether the route it was triggered for has *already* resolved by the time it runs, and skips dispatching "started" entirely if so).
  - **`SAFETY_TIMEOUT_MS` is `20_000`, not something short** — deliberately. It's a last-resort backstop for a navigation that never resolves at all (swallowed error, same-route soft nav), NOT a cap on how long a legitimately slow navigation is allowed to take. At its old value (4000ms) it was confirmed live to fire on a genuinely working navigation — a heavier route compiling for the first time in `next dev` took 10+ real seconds (user-reported + DevTools-screenshot-confirmed: NOT a backend/DB problem — the actual API calls on the same page returned in 50-66ms; this is Next.js dev-mode's one-time, per-route, on-demand compile, which doesn't exist in a production build and only fires once per route per dev-server lifetime). Since the underlying `_rsc` fetch isn't tracked by `pendingRequests` at all, once the safety timeout force-cleared `navigationPending`, nothing was left to keep the loader up for the remaining several seconds — it fell silent while the OLD page just sat there, the exact failure mode this component exists to prevent. A too-long safety timeout costs nothing (it essentially never fires); a too-short one actively lies about completion. If you ever see this fire in normal use, that's a real bug to chase, not a signal to shorten the timeout back down.
  - **Same-URL `pushState`/`replaceState` calls are now a no-op** (`isSameUrl()`, checked at the top of `notifyStart()`) — `router.refresh()` (re-fetch the current route, no navigation) is exactly this: same URL, pathname never changes. Before this fix, EVERY `pushState`/`replaceState` call — same-URL or not — unconditionally started the "navigating" flag, and since the `[pathname, searchParams]` clearing effect only fires on an actual route change, a same-URL call left the flag stuck until the (now 20s) safety timeout. Confirmed live: a branding-image upload's `router.refresh()` (called after its own success toast, to refresh the sidebar logo etc.) was popping the global loader back up right after "Image uploaded" — user-screenshotted, and reproduced with a script watching the 4 seconds after the toast. This fix is call-site-agnostic — it protects every OTHER place that calls `router.refresh()` after a mutation too, not just this one.
  - **The backdrop is deliberately `pointer-events-none`, never blocking** even though it visually covers the full viewport (a `framer-motion`-faded dark scrim behind the `GymLoader` card) — `pendingRequests` also ticks up for background work the user never triggered (e.g. `use-notifications.ts`'s 60s `refetchInterval`, or a still-in-flight fetch on the page being navigated away from); an earlier blocking version (`FullScreenLoader`, opaque backdrop) was confirmed live under throttled network to occasionally trap every click on the page behind an invisible, user-uninitiated request.
  - **If you ever add another global signal into `ui-slice` or touch this provider, verify it live under CDP network throttling (`Network.emulateNetworkConditions`) and by routing/delaying a specific request (Playwright `page.route()`) the same way** — this exact class of bug (stuck state, missing trigger window, blocking clicks) is invisible to typecheck/eslint/vitest and even to a normal-speed manual click-through.
  - **Opting a request OUT of the global loader — `silent: true`**: `api-client.ts` module-augments `AxiosRequestConfig` with a `silent?: boolean` field; the request/response interceptors check it before dispatching `requestStarted`/`requestFinished`, so a `silent: true` call never contributes to `pendingRequests` at all. Use this for any request that already has its own local, in-place loading UI — the global full-screen loader on top of that is redundant and can visually cover the exact element the user is watching (confirmed user-reported: uploading a branding image blanked the whole screen, hiding the other upload buttons). Applied to every "upload starts immediately on file select" call site (the 3 branding image endpoints, member-document upload) — NOT to uploads that just stage a data-URL into local form state for a later Save (avatar, expense receipts, exercise images), which are correctly covered by the global loader already. `ImageUploadField` (`features/gym-settings/components/image-upload-field.tsx`) is the reference implementation for what replaces the global loader in this case: `onUpload` is `(dataUrl, onProgress) => Promise<void>`, so the field's own `uploading` state spans the whole upload (not just the client-side canvas-downscale step), and a real progress bar (axios `onUploadProgress`, not simulated) renders directly on the image thumbnail + "Uploading… N%" on the button.
