# Backend Guide (`apps/api`)

Express + TS + Prisma + Postgres + Redis + BullMQ. Clean architecture: **routes → controller → service → repository**, per-feature modules under `src/modules/`.

## Core conventions (follow these exactly)

- **Module layout** (plural dirs): `controllers/ services/ repositories/ routes/ validators/ dto/ events/ interfaces/`. Smallest reference module: `modules/branches`. DI-style reference: `modules/authentication` (`utils/auth-module.factory.ts` builds per-request, tenant-bound service).
- **Response envelope**: `sendSuccess(res, data, message?, status?)` / errors thrown as `AppError` subclasses (`core/errors/app-error.ts`: ValidationError 422, NotFoundError 404, ConflictError 409, ForbiddenError 403, UnauthenticatedError 401, RateLimitedError 429) with codes from `core/errors/error-codes.ts`. Never hand-roll JSON.
- **Validation**: zod schemas in `validators/*.validators.ts`, wired with `validate({ body?, query?, params? })` — it PARSES AND REPLACES req fields (coercion applies).
- **Routes**: local `asyncHandler` helper (copy from any routes file), `authenticateMiddleware` then `requirePermission('key')`.
- **Swagger `@openapi` JSDoc trap**: multi-line block YAML is fine; single-line compact annotations MUST be wrapped in one outer flow mapping: `/** @openapi { "/path": { get: {...} } } */` — a bare `/path: get: {...}` one-liner breaks YAML parsing. Quote strings containing `—` or `:` inside flow mappings.
- **Tenant scoping**: `getTenantScopedClient(tenantId)` wraps every query in `set_config('app.tenant_id')` + RLS. Raw `prisma` ONLY for global catalogs / genuinely cross-tenant platform work — always with a comment noting the dev-superuser-bypasses-RLS caveat. **Never batch multiple calls into `this.db.$transaction([...])`** on this client — each call already opens its own nested `set_config`+query transaction, so a batched array silently drops the writes (found live in Prompt 17's §Workout Management — use plain sequential `await`s instead).
- **Events**: in-process `eventBus` (`core/events/event-bus.ts`), `emitEvent`/`onEvent`; listeners registered in `server.ts` bootstrap (`register*Listeners()` per module `events/` dir).
- **Email**: `enqueueEmail({to,subject,html})` → BullMQ queue `notifications-email`; templates in `infrastructure/mail/templates/` (branded via `tenantService.resolveById`). Dev SMTP = Mailpit.
- **Rate limiting**: `createRateLimiter({windowMs,max,prefix,keyGenerator?,skip?})` — Redis-backed, key default `tenantId:ip`, auto-disabled under `NODE_ENV=test`. Per-endpoint limiters (login/register/OTP/password-reset) stack with `apiRateLimiter()` (Prompt 36), a 300/min-per-key global backstop mounted in `app.ts` right before the `v1Router` mount — covers every route that previously had none. Gateway webhooks are exempted via `skip` (legitimate retry bursts, already authenticated by signature).
- **Object storage** (`core/storage/`, Prompt 37): `uploadDataUrl(dataUrl, {keyPrefix, visibility: 'public'|'private', accept?: ('image'|'pdf')[]})` is the one funnel point for every file upload — `public` returns a stable direct URL (drop-in replacement for the old data-URL, zero read-path changes); `private` (member documents, expense receipts) returns a bare object key, which callers MUST turn into a fresh `presignGetUrl(key)` on every read — never persist a private URL. `isDataUrl(value)` distinguishes a fresh upload from an unchanged resubmitted value on update paths. Gracefully no-ops (returns the input unchanged) when `env.storage.isConfigured` is false — never a hard requirement. MinIO in dev (`docker compose up minio minio-init`), real S3/R2 in prod via the same `@aws-sdk/client-s3` client. **Magic-byte validation (Prompt 40)**: `uploadDataUrl` sniffs the buffer's real file signature (`core/storage/file-signature.util.ts#sniffFileType`) and rejects (`ValidationError`, 422) anything that doesn't match — the client-claimed MIME prefix is never trusted for `ContentType`/extension, the sniffed type is. Runs even when storage isn't configured (content-safety, not an object-storage concern). `accept` defaults to `['image']`; only member-documents and expense-receipts pass `['image', 'pdf']`. No SVG support anywhere in this pipeline — it has no binary magic-byte signature to verify, so it's disallowed rather than half-validated.
- **Error tracking/APM** (`core/observability/sentry.ts`, Prompt 37): `captureError(err, extra?)`, no-ops unless `SENTRY_DSN` is set. Already wired into `errorHandlerMiddleware` (5xx only) and `process.on('unhandledRejection'|'uncaughtException')` in `server.ts` — don't add new capture call sites elsewhere unless they're genuinely otherwise-unobserved.
- **Security headers / CSP** (`app.ts`, Prompt 41): app-wide `helmet()` sets a fully explicit, maximally locked-down CSP (every directive `'none'`) in every environment — this is a pure JSON API, nothing it returns legitimately needs to load a script/image/frame. `/api/docs` (Swagger UI) gets a SECOND `helmet()` call scoped to that path with its own more permissive CSP (Swagger's bundled UI needs inline script/style) — a second `helmet()` call's `res.setHeader` genuinely replaces the first; `contentSecurityPolicy: false` would NOT undo an already-set header from earlier middleware. Adding a new HTML-serving route later needs the same override pattern, not a weakening of the app-wide default.
- **User-content sanitization** (`core/security/html-sanitizer.util.ts`, Prompt 41): `sanitizeRichText(html)` wraps `sanitize-html` with an allowlist scoped to exactly what `RichTextEditor`'s toolbar can produce (bold/italic/underline/list/link) — the only current write path is `TenantAnnouncementService#create`/`#update`. Any FUTURE feature that persists user-authored HTML for later `dangerouslySetInnerHTML` rendering must sanitize at its write path the same way, not add a second escaping step at render time — the render side trusts the database unconditionally by design.
- **Tests**: Vitest, `src/**/*.spec.ts` only. Integration specs hit the real dev DB.

## Request context

`tenantMiddleware` (global) resolves subdomain / `X-Tenant-Slug` → `req.tenant` (`ResolvedTenant`). `authenticateMiddleware` verifies Bearer JWT → `req.auth` (`AccessTokenClaims`: `sub`, `tenantId`, `role`, `roles[]`, `permVer`, `sid`, `jti`) and asserts `req.tenant.id === claims.tenantId`. Admin portal uses `req.admin` via a separate stack — never mix.

**Billing rescue path**: `assertTenantAccessible` blocks expired trials/subscriptions with 402 on every route EXCEPT `EXPIRY_EXEMPT_PREFIXES` (`/auth`, `/subscription`, `/billing`, `/payment`, `/coupon`, `/invoice` — see `tenant.middleware.ts`), so an expired owner can still log in and pay (`POST /subscription` reactivates tenant + subscription). Suspension/maintenance block everything. Frontend counterpart: trial/subscription-expired status screens link to `/billing` (or `/login` when signed out), and the axios interceptor suppresses expiry redirects while on `/billing`.

## Authorization (the IAM engine — Prompt 11)

**Permission format: `resource:action`** (e.g. `members:read`) — NOT dot format. Catalog seeded in `prisma/seed.ts` (`PERMISSIONS` + `ROLE_PERMISSIONS`); 6 system roles (`tenantId NULL, isSystem`): SUPER_ADMIN, OWNER, MANAGER, TRAINER, RECEPTIONIST, MEMBER. Custom roles are tenant rows.

- **Effective permissions** = union(role perms) + user GRANT overrides − user DENY overrides (DENY always wins). Pure logic: `modules/permissions/utils/effective-permissions.util.ts`; computed in `authentication/repositories/role.repository.ts#getPermissionKeysForUser`.
- **Caching**: Redis `perm:{userId}:{permVer}` (TTL 30m). `permVer` is PERSISTED on `users.permission_version`. `bumpPermissionVersion` increments it AND deletes the old cache key → permission changes bite on the next request even for live tokens.
- **Enforce** with `requirePermission('key')` (middleware) or `permissionEngine` (`modules/permissions/services/permission-engine.service.ts`) for programmatic checks. Role checks: `requireRole(...)` — prefer permissions.
- **Branch access**: `users.all_branches` bool or `user_branches` rows (with `is_primary`, `expires_at` for temporary). Guard single-branch routes with `requireBranchAccess()` / scope queries via `getBranchAccess(tenantId,userId)` (`authentication/middlewares/branch-access.middleware.ts`).
- **Audit**: every IAM write calls `AuditLogRepository.record` (actions `iam.*`) with `actorFrom(req)` (`authentication/utils/actor.util.ts`). Read side: `GET /audit-logs` (perm `audit:read`).

**Any new module (Members, Attendance, …) must**: take `requirePermission` on routes, use `getTenantScopedClient`, write audit records for mutations, and scope branch-sensitive queries via `getBranchAccess`.

## Settings (Gym Profile, Branding & Business Settings — Prompt 12)

`modules/settings/` — same routes→controller→service→repository layout as every other module, but the service (`SettingsService`) fronts FOUR separate 1:1-with-tenant tables through one class, constructed per-request as `new SettingsService(req.tenant!.id, req.tenant!.slug)`:

- `TenantProfile` (new table) — legal/registration/GST-VAT/business-type/description, contact (email/phone/alternatePhone/website/address/city/state/country/postalCode/lat/lng), `businessHours` (Json), `socialLinks` (Json). **Distinct from the pre-existing `BillingAddress`** (P8) — that's FitCloud's billing address *for* the tenant; this is the tenant's own gym address shown to its members.
- `TenantSettings` (extended) — gained `currencySymbol`, `dateFormat`, `timeFormat`, `weekStartDay`, `measurementUnit` (enum METRIC/IMPERIAL), `emailNotificationsEnabled`/`pushNotificationsEnabled`/`smsNotificationsEnabled`, `smsProviderConfig` (Json?, config-only — no SMS actually sends yet).
- `TenantBranding` (extended) — gained `theme` (enum LIGHT/DARK/SYSTEM), `loginBackgroundUrl`, `dashboardBannerUrl`, `emailLogoUrl` (alongside pre-existing logoUrl/faviconUrl/primaryColor/secondaryColor/welcomeMessage). **P33 gap fix**: those 3 columns (plus `faviconUrl`, which WAS present but never actually rendered) were fully stored/uploadable from day one but never reached anything that used them — `ResolvedTenant`/`ResolvedTenantRecord` (`modules/tenants/interfaces/tenant.interface.ts`) only declared 6 of the 9 `TenantBranding` columns, and `toResolvedTenant()` only mapped those 6, even though Prisma's `RESOLVE_INCLUDE.branding: true` was already fetching the full row — a type/mapping gap, not a query gap. If you add a new `TenantBranding` column that anything OUTSIDE the gym-settings page itself needs to read, it must be added to `ResolvedTenant.branding` + `ResolvedTenantRecord.branding` + `toResolvedTenant()`'s mapping, or it'll silently never reach `req.tenant`/the frontend's `useTenant()`/`TenantProvider` the way `logoUrl`/`primaryColor` do — the gym-settings `/settings/branding` GET is a completely separate read path that already saw every column correctly.
- `TenantInvoiceSettings` (new table) — `invoicePrefix` (default "INV"), `invoiceFooter`, `taxPercentage`, `defaultPaymentTermsDays`. **Distinct from the platform `Invoice` model** (P8) — that's FitCloud invoicing the tenant for its subscription; this is defaults for invoices the tenant will issue to its own members (Payments module, not yet built).

Both new tables got hand-written RLS migrations (`20260721092400_enable_rls_gym_settings`) per the hard rule.

Endpoints are consolidated by REST resource rather than 1:1 with the prompt's 18 named capabilities (e.g. Currency/Timezone/Date-Time-Format/Language all PATCH the same `/settings/business`; Tax Information PATCHes `/settings/invoice`) — see the Swagger comments in `routes/settings.routes.ts` for the capability→endpoint mapping. Routes: `GET/PATCH /settings/profile`, `PATCH /settings/profile/contact`, `PATCH /settings/profile/business-hours`, `PATCH /settings/profile/social-links`, `GET/PATCH /settings/business`, `GET/PATCH /settings/branding`, `POST /settings/branding/logo`, `POST /settings/branding/favicon`, `POST /settings/branding/upload` (generic, `field` selects loginBackgroundUrl/dashboardBannerUrl/emailLogoUrl), `GET/PATCH /settings/invoice`, `GET/PATCH /settings/email`, `GET/PATCH /settings/notifications`.

**Permissions**: `settings:read` (new, seeded this prompt, granted to MANAGER alongside existing `settings:manage`) gates all GETs; `settings:manage` (pre-existing) gates all writes.

**Uploads**: no object storage exists — same pattern as IAM avatars. Client canvas-downscales to a JPEG data-URL before sending; API just stores/returns the data-URL string (validated by a data-URL regex + ~300KB cap in `uploadImageSchema`). "Public URL" in the prompt spec = the data-URL itself.

**Cache invalidation — load-bearing**: any write that touches `gymName`, `TenantBranding`, or `TenantSettings` MUST call `tenantService.invalidateCache(tenantSlug, tenantId)` (see `SettingsService#invalidateTenantCache`), because `tenantMiddleware` gates every request on the cached `ResolvedTenant`, and the public `/public/tenants/resolve` + login-screen branding read from that same cache. Verified live: PATCHing gym name/primary color and immediately re-querying `/public/tenants/resolve` reflects both instantly.

**Audit**: every mutating method logs via `AuditLogRepository.record` under `settings.*` actions (e.g. `settings.profile.update`, `settings.branding.upload-logo`) — same `actorFrom(req)` pattern as IAM.

## Staff Management (Manager/Trainer/Receptionist — Prompt 13)

`modules/staff/` — routes→controller→service→repository, same shape as every other module, but `StaffService` composes the **existing** IAM repositories rather than reimplementing account CRUD:

- `UserManagementRepository` (from `modules/users`, imported unmodified) handles create/update/setStatus/softDelete/restore/setRoles/setBranches/findByEmail/findByPhone/ownerUserIds — reused as-is.
- `StaffProfileRepository` (new, in this module) owns the 1:1 `StaffProfile` table: `employeeId` (unique per tenant, auto-generated as `EMP-0001`, `EMP-0002`, … via a count-based sequence with retry-on-conflict — editable afterward), `firstName`/`lastName` (kept off `User` itself; `User.name` is derived as `"${firstName} ${lastName}"` so every other part of the app — auth, sessions, audit, notifications — keeps working against the field it already expects), gender, dateOfBirth, joiningDate, address, notes, and the Employment Information group (employmentType/salaryType/salaryAmount/shift/weeklyOff/workStatus enums+fields).
- `StaffRepository` (new) does the role-filtered `User` joins for list/detail (`userRoles.some({role:{name: in ['MANAGER','TRAINER','RECEPTIONIST']}})` + `staffProfile: true` include) — kept separate from `UserManagementRepository`'s generic list/detail so the generic Users/IAM screens are untouched (zero regression risk).
- Emergency contact, avatar, and account status (`ACTIVE`/`SUSPENDED`/`DEACTIVATED`/`PENDING_VERIFICATION`/`LOCKED` + soft-delete) all reuse the existing `User` columns from IAM (Prompt 11) — **not** duplicated onto `StaffProfile`.

**Staff types**: exactly `MANAGER` | `TRAINER` | `RECEPTIONIST` (`STAFF_ROLE_NAMES` in `dto/staff.dto.ts`) — the Owner already exists via the `OWNER` system role and is never touched here. A staff member holds exactly one of these three roles (unlike generic Users, which can hold several) and always has an explicit branch list with exactly one primary (`allBranches` is forced `false` — no "all branches" shortcut like generic IAM users get).

**Create Staff → activation flow (the one genuinely new piece of infrastructure)**: unlike the existing `invitations` module (which creates the `User` row only when the invite is *accepted*), Create Staff needs the full profile/employment data up front, so it creates the `User` row immediately (`status: PENDING_VERIFICATION`, an unusable random password) and then mints an activation link using the **PasswordReset** token machinery (`VerificationRepository.createPasswordReset` + `hashToken`/`generateOpaqueToken` from `core/security/token.util.ts`) instead of the `UserInvitation` table — a 7-day-TTL token (`STAFF_ACTIVATION_TTL_HOURS`) rather than the 48h invite / 30-min reset-password TTLs. The email reuses the **existing invitation email template** (`buildInvitationEmail`, re-exported from `authentication/events/auth-email.listeners.ts` for exactly this kind of reuse) via a new `staff.activation_requested` event + listener (`staff/events/staff-email.listeners.ts`, registered in `server.ts`), pointing the accept link at `/staff-activation/{token}` instead of `/invitation/{token}`. `POST /staff/activation/accept` (public) consumes the token via the same `consumePasswordReset` used by self-service "forgot password", sets the password, and flips `PENDING_VERIFICATION → ACTIVE` — this is "Set Password" + "Activate Account" from the prompt spec in one step. `POST /staff/:id/reset-password` (admin-triggered "Reset Password") is a thin wrapper that reuses `AuthEvents.PasswordResetRequested` + the **existing** password-reset email listener verbatim — no new template needed there.

**Subscription staff limits — built from scratch**: before this prompt, `TenantLimit.maxManagers/maxTrainers/maxReceptionists/maxStaff` were written at provisioning time but **never read anywhere** — no enforcement existed. `StaffService#assertStaffCapacity(role)` now checks both the per-role cap and the total-staff cap on every Create Staff / Assign Role call, comparing against a live `COUNT` of non-deleted users holding that role. Verified live: creating a 6th MANAGER on a plan with `maxManagers: 5` is correctly rejected with `409 CONFLICT`.

**Permissions**: `staff:view`, `staff:create`, `staff:update` (also gates the admin-triggered Reset Password action), `staff:delete`, `staff:restore`, `staff:activate` (covers activate/deactivate/suspend — the spec didn't need separate keys for each transition), `staff:invite` (send/resend activation), `staff:assign-branch`, `staff:assign-role` — all granted to MANAGER in the seed, none to TRAINER/RECEPTIONIST (staff don't manage other staff).

**Business rules enforced**: email/phone/employeeId unique per tenant (service-layer checks, same pattern as Users); one primary branch required (`assignBranches` rejects a `primaryBranchId` not in `branchIds`); suspended/deactivated staff can't log in (falls out of the existing `AuthService` status check on `User.status` — no new code needed); soft delete only (`deletedAt` + status flip, restorable).

**Found and fixed while verifying this module**: the API's CORS `methods` allow-list (`app.ts`) was missing `PUT` — this silently blocked every PUT-based action from a real browser, including the **already-shipped** IAM roles/branches assignment buttons (`PUT /users/:id/roles`, `PUT /users/:id/branches`), not just this module's new `PUT /staff/:id/role` / `PUT /staff/:id/branches`. Fixed by adding `'PUT'` to the `methods` array. This had apparently never been caught because no prior live E2E happened to click those specific IAM buttons in a browser (curl-based smoke tests don't enforce CORS).

## Member Management (Prompt 14)

`modules/members/` — two routers: `member.routes.ts` (mounted `/members`) and `membership-plan.routes.ts` (mounted `/membership-plans`), sharing the module's `dto/`, `validators/`, `repositories/`.

**`Member` is a standalone table, NOT a `User` row** — deliberately different from Staff Management. The prompt for this module had no invitation/password/login-flow section (unlike Staff's explicit "Invitation Flow"), so a member here is a pure gym-membership record with its own `MemberStatus` (`ACTIVE`/`INACTIVE`/`FROZEN`) — nothing to authenticate. The pre-existing `MEMBER` system role + its permissions (seeded in Prompt 5: `profile:read`, `bookings:*`, `payments:read`, `chat:use`) stay reserved for a genuinely future member-facing portal that would create real `User` rows at that time — don't conflate the two.

- `MemberRepository` — role-analogous to Staff's `StaffRepository`: joins `branch`, `trainer` (a `User`), `memberships` (full history + `plan`), `freezes` for both list and detail (one include set, `toListItem`/`toDetail` just slice differently — a member's membership count is small enough that this isn't a real cost).
- `MembershipRepository` — `Membership` (one row per period) + `MembershipFreeze` CRUD. Renew/Upgrade never mutate an existing `Membership` row; they flip its status to `SUPERSEDED` and `create()` a new `ACTIVE` one, so "Renewal History" is just `member.memberships` ordered by `createdAt` — no separate history table.
- `MembershipPlanRepository` — the gym's own plan catalog (`MembershipPlan`: name/durationDays/price/isActive). **Distinct from `SubscriptionPlan`** (Prompt 7/8, FitCloud's plan catalog for billing the tenant) — same naming-collision caution as `TenantProfile`/`TenantInvoiceSettings` vs `BillingAddress`/`Invoice` in Prompt 12.
- `MemberDocumentRepository` — `MemberDocument` rows, same inline-data-URL-no-object-storage pattern as everything else in this codebase.

**Membership lifecycle business rules**:
- **One active membership per member** — `assignMembership` throws `409` if a `Membership` with `status: ACTIVE` already exists; caller must Renew or Upgrade instead.
- **Renew**: supersedes the current membership; new `startDate` = old `endDate` if not yet expired (contiguous), else `now` (no gap-filling for a lapsed member) — `endDate = startDate + plan.durationDays`.
- **Upgrade**: supersedes the current membership; new period always starts `now` regardless of the old end date (upgrading takes effect immediately, no waiting out the old plan).
- **Freeze/Unfreeze**: `MembershipFreeze` row created/closed (`unfrozenAt`), `Member.status` flips `ACTIVE ⇄ FROZEN`. `MemberDetailDto.canCheckIn` is a computed, **informational-only** field (`status===ACTIVE && activeMembership.endDate >= now`) — there's no Attendance module yet to actually enforce "frozen/expired members cannot check in," so this just gives the frontend (and a future Attendance module) something to read.

**QR codes**: `qrcode` npm package (newly added this prompt — nothing existed for this before) generates a PNG data-URL server-side from `` `fitcloud-member:${tenantId}:${qrCodeToken}` `` (`qrCodeToken` = `generateOpaqueToken(16)`, same token util as everywhere else). Generated at Create Member time and cached on the row (`qrCodeImageUrl`); `POST /members/:id/qr-code` regenerates both token and image (invalidates any previously-printed/scanned code).

**Trainer/Branch integration**: `trainerId` is a plain FK to `User.id`, validated at write-time to hold the `TRAINER` role in this tenant (`assertTrainerValid` — reuses the exact `userRoles.some({role:{name:'TRAINER'}})` shape from Staff Management, no new Staff-module code needed). `branchId` reuses the existing `Branch` table/validation from `modules/branches`.

**Subscription member limits**: `MemberService#assertMemberCapacity()` mirrors Staff Management's `assertStaffCapacity` pattern exactly — reads `TenantLimit.maxMembers`, counts non-deleted `Member` rows, rejects with `409` at the cap. Verified live by temporarily lowering a tenant's `maxMembers` to 1 and confirming the 2nd create is rejected.

**Permissions**: `members:view`, `members:create`, `members:update` (also covers activate/deactivate/freeze/unfreeze/branch-transfer/QR-regenerate/document upload-delete — the spec's 9 keys didn't include separate ones for these), `members:delete`, `members:restore`, `members:import`, `members:export`, `members:assign-trainer`, `members:assign-membership` (covers assign/renew/upgrade) — granted in full to MANAGER; RECEPTIONIST gets view/create/update/import/export/assign-membership (no delete/restore/assign-trainer, matching the front-desk trust level already established for `members:manage` pre-Prompt-14); TRAINER gets view only. **Note**: the pre-existing speculative `members:read`/`members:manage` keys from the Prompt-5 catalog are untouched (still seeded, still granted) but no route uses them anymore — the new granular keys are what's actually enforced. Membership Plan CRUD reuses the pre-existing `memberships:manage` permission verbatim rather than adding a redundant key.

**Documents**: images go through the same client-side canvas downscale as everywhere else (`fileToDataUrl`); PDFs/other files can't go through a canvas, so a new `fileToRawDataUrl(file, maxBytes)` (same file, `lib/image-to-data-url.ts`) reads them as-is via `FileReader`, capped at 2MB. Backend validator (`uploadMemberDocumentSchema`) accepts any `data:<mime>;base64,` prefix (not just images) up to ~2.2MB of base64 text.

**`MembershipPlan` field additions** (all on the same table, `membership_plans`): `planCode` (auto-gen `PLAN-0001`-style + editable, unique per tenant, same count-based-sequence-with-retry pattern as Staff's `employeeId`/Member's `memberId`), `category`, `durationValue`+`durationType` (new `DurationType` enum: DAYS/WEEKS/MONTHS/YEARS — replaces the Prompt 14 assumption that duration is always expressed in days), `joiningFee`/`taxPercentage`/`discountPercentage`, `displayOrder`, `notes`, `deletedAt` (soft delete — **did not exist on this model before Prompt 15**, Prompt 14's plans were hard-catalog-only), and two field groups:

**New member-side membership lifecycle** (on `MemberService`, same file as Prompt 14's assign/renew/upgrade):
- **Downgrade** — literally the same code path as Upgrade (`private changePlan()`), just a different audit action tag (`member.membership_downgraded` vs `_upgraded`) and route (`POST /members/:id/membership/downgrade`) — there is no meaningful business-logic difference between "upgrade" and "downgrade," both supersede the current membership and start a new one effective immediately.
- **Extend** — `POST /members/:id/membership/extend` `{days}` — adds days to the CURRENT membership row's `endDate` in place (no supersede, no new row — this is a correction/bonus on the existing period, not a new period, so it does NOT show up as a separate Renewal History entry).
- **Cancel** — `POST /members/:id/membership/cancel` — flips the current `ACTIVE` membership to `CANCELLED` (an enum value that existed since Prompt 14 but was never actually reachable from any route until now).
- **Resume** — `POST /members/:id/resume`, a straight alias calling the exact same `unfreeze()` service method Prompt 14 already built; the old `POST /members/:id/unfreeze` route is UNTOUCHED (kept for backward compatibility) — both routes now exist side by side.

**New business-rule enforcement in `assignMembership`/`renewMembership`** (private helpers `assertPlanAssignable`/`assertRenewalWindow` on `MemberService`):
- Plan purchase window (`validityStart`/`validityEnd`) — rejects assign/upgrade/downgrade outside the plan's own availability window.
- Age eligibility (`minAge`/`maxAge`) — computed from `Member.dateOfBirth` at assignment time (calendar-correct, accounts for whether the birthday has occurred yet this year); silently skipped if the member has no recorded DOB (can't validate what you don't know).
- Renewal window (`renewalWindowDays`) — a renew is rejected if attempted more than `renewalWindowDays` before the current membership's `endDate` (`0` = no restriction, anytime). Verified live: assigning a plan with `renewalWindowDays: 15` and immediately trying to renew it (membership just started, months from expiry) is correctly rejected with a 422 explaining the window.
- Auto-renewal — `assignMembership` rejects `autoRenew: true` if the plan's `autoRenewalAllowed` is false.

**Permissions**: `memberships:view`, `memberships:create`, `memberships:update` (also covers activate/deactivate/duplicate — no separate keys needed), `memberships:delete`, `memberships:restore`, `memberships:assign`, `memberships:renew` (also covers extend), `memberships:upgrade` (also covers downgrade and cancel — all three are "change what plan/state the current membership is in"), `memberships:freeze` (also covers resume). MANAGER is granted all 9 new keys (zero regression — MANAGER already had `members:assign-membership` covering the same actions). RECEPTIONIST is granted view/assign/renew/upgrade/freeze but deliberately **not** create/update/delete/restore — plan-CATALOG changes stay a Manager-only decision, a real tightening versus the old blanket `memberships:manage` RECEPTIONIST held before (RECEPTIONIST could previously create/edit plans; can no longer). TRAINER is granted view only. Membership Plan CRUD itself (`memberships:create`/`update`/etc.) is enforced on `membership-plan.routes.ts`; the pre-existing `memberships:manage` key (from the Prompt-5 speculative catalog) is left seeded/granted but unused by any route now, exactly like the P14 precedent.

## Attendance Management (Prompt 16)

New `modules/attendance/` — same routes→controller→service→repository shape as every other module. New table `attendance_records` (RLS'd via hand-written migration `20260721184500_enable_rls_attendance`, right after the model migration `20260721184450_attendance_management_module`, same two-migration pattern as every other new tenant-scoped table): `memberId`/`branchId`/`checkInTime`/`checkOutTime`/`attendanceDate` (`@db.Date`, stamped in the check-in **branch's own** timezone, not server time)/`method`/`deviceName`/`deviceId`/`status`/`notes`/`checkedInBy`/`checkedOutBy` (staff attribution for manual actions, null for self-service)/soft-delete.

**Two endpoint pairs, one shared implementation**: `POST /attendance/check-in|check-out` (self-service — QR scan) and `POST /attendance/manual-check-in|manual-check-out` (front-desk) both funnel into private `performCheckIn`/`performCheckOut` on `AttendanceService`; the only difference is `checkedInBy`/`checkedOutBy` gets set to `actor.userId` on the manual pair and stays `null` on the self-service pair. `POST /attendance/validate-qr` looks up a member by `qrCodeToken` (reuses `MemberRepository.findByQrToken` from Prompt 14's QR generation) and returns eligibility/`alreadyCheckedIn` **without** recording anything — it's a read-only preview the scanner UI calls before showing the Check-in/Check-out action button.

**Business rules, all enforced in `AttendanceService`**:
- `eligibility(member)` — active status, non-`FROZEN`, has an `ACTIVE` membership, membership `endDate >= now` — reuses the exact same shape of check already used for `MemberDetailDto.canCheckIn` (Prompt 14's informational-only field; this module is what finally *enforces* it).
- One open check-in per member — `AttendanceRepository.findOpenByMember` (status `CHECKED_IN`, `checkOutTime: null`); check-in throws `409 CONFLICT` if one is found. Check-out throws `409` if none is found.
- Branch scoping — `requireBranchAccess('branchId')` middleware (existing, from IAM) plus a service-level `assertBranchAccess` re-check; a member can only be checked in at their own assigned branch (`branchId !== member.branchId` → `409`) unless the input omits `branchId`, which defaults to the member's own branch.
- Tenant/branch timezone — new zero-dependency `utils/timezone.util.ts` (`Intl.DateTimeFormat`, no new package): `dateInTimezone(timezone, at)` stamps `attendanceDate`, `hourInTimezone(timezone, at)` buckets the "peak check-in hour" stat. Per-check-in stamping always uses that specific `branchTimezone(branchId)`; when a query has **no** branch filter (the all-branches dashboard default) there's no single branch to key off, so a `defaultTimezone()` helper falls back to the tenant's `isDefault` branch (same `orderBy: [{isDefault:'desc'},{name:'asc'}]` convention as `BranchRepository.list()`) — **not** hardcoded UTC (see bug note below).

**Dashboard summary** (`GET /attendance/summary`, optional `branchId`/`dateFrom`/`dateTo`): `totalCheckInsToday`/`totalCheckOutsToday`/`currentlyInside` (single `countForDate` repository query), `peakCheckInHour` (bucketed via `hourInTimezone` over today's check-in timestamps), `trend` (7-day-default rolling count, gap-filled with zeros via `fillTrendGaps` so the chart never shows a missing data point as absent vs. genuinely zero).

**Bug found + fixed during live real-time verification**: `getSummary`/`getToday` both used to fall back to hardcoded `'UTC'` for "today" whenever no `branchId` filter was supplied, while `performCheckIn` always stamps `attendanceDate` in the **actual check-in branch's** timezone. For any branch not on UTC, a fresh check-in on the default (all-branches) dashboard view could land on a different `attendanceDate` than the summary query's UTC-computed "today," silently excluding it from `totalCheckInsToday` even though `currentlyInside` (not date-bucketed) updated correctly — caught by a two-tab Playwright test where "Currently inside" changed live but "Check-ins today" didn't move. Fixed by adding the `defaultTimezone()` helper described above.

**Real-time**: `emitToTenant(tenantId, 'attendance:checkin', dto)` / `emitToTenant(tenantId, 'attendance:checkout', dto)` fire on every successful mutation (both self-service and manual) — reuses the existing Socket.IO server (`infrastructure/realtime/socket-server.ts`) verbatim, no new transport. The app-wide `RealtimeProvider` (tenant-web) already listened for both event names from an earlier prompt's scaffolding; it invalidates the `['attendance']` TanStack Query key prefix on either event, which covers every attendance hook (`list`/`today`/`summary`/`member`/`branch` all key off that same prefix) — so the dashboard, history, and member-detail views all refresh live in any open tab with zero polling and zero new frontend socket-wiring needed.

**Permissions**: `attendance:view`, `attendance:checkin`, `attendance:checkout`, `attendance:update`, `attendance:delete`, `attendance:export` — distinct from the pre-existing speculative `attendance:create`/`attendance:read` (left seeded but unused, same precedent as Membership Plans superseding the old blanket `memberships:manage`). MANAGER gets all 6. RECEPTIONIST gets view/checkin/checkout/export only — front-desk operations, record correction/deletion stays Manager-only (same tightening pattern as Membership Plans/Staff). TRAINER gets view/checkin/checkout only (no export).

**Verified live**: full API vitest suite 97/97 (including new `attendance.validators.spec.ts`, 16 tests covering the check-in/check-out/QR/list/update schemas); live curl + Playwright covering QR validate→check-in/out, manual check-in/out, duplicate check-in correctly rejected with `409`, membership/frozen/expired eligibility rejections, branch-mismatch rejection, History search/filters, the Member-detail "Recent visits" card, and a two-tab real-time test proving dashboard counters update without a reload — zero unexpected console errors.

**Weekly schedule replace** (`PATCH /workout-plans/:id/exercises`, `{ exercises: [...] }`) replaces the ENTIRE schedule in one call — array order becomes `sortOrder` within each day, which is how the frontend's drag-and-drop persists a reorder (delete everything, recreate in the new order). **Bug found + fixed during live testing**: `WorkoutPlanRepository.replaceExercises()` originally batched the delete+creates via `this.db.$transaction([...])` — but `getTenantScopedClient` (see "Core conventions" above) already wraps every individual call in its OWN nested `set_config`+query transaction for RLS session-variable scoping, and nesting a batched `$transaction` array on top of that silently dropped every write: the endpoint returned `200 OK` with the "updated" plan, but a subsequent `GET` showed zero exercises, and a Duplicate of that plan copied zero exercises too. Fixed by rewriting it as plain sequential `await`s in a `for` loop (with an `eslint-disable-next-line no-await-in-loop`, since order must be preserved for `sortOrder`) — matching every OTHER repository in this codebase, none of which use `$transaction` for exactly this reason. **If a future module needs real multi-statement atomicity against the tenant-scoped client, this needs a different approach** (e.g. a raw `$transaction` that itself does the `set_config` once at the top, rather than relying on `getTenantScopedClient`'s per-call wrapping) — not solved by this prompt, just worked around.

**Permissions**: `workouts:view`, `workouts:create`, `workouts:update`, `workouts:delete`, `workouts:restore`, `workouts:assign`, `workouts:progress` — distinct from the pre-existing speculative `workout-plans:manage` (left seeded but unused, same precedent as every prior module). MANAGER gets all 7. ## Diet & Nutrition Management (Prompt 18)

New `modules/diet/` — same two-router shape as Workout Management (`food.routes.ts` mounted at `/foods`, `diet-plan.routes.ts` mounted at `/diet-plans`), same routes→controller→service→repository layout. Five new tables, RLS'd via a hand-written migration (`20260723093500_enable_rls_diet_nutrition_management`, right after the model migration `20260723093411_diet_nutrition_management_module`):

- **`Food`** — the reusable food library: name (unique per tenant), category, servingSize, calories, protein/carbohydrates/fat/fiber/sugar/sodium (all `Decimal`), notes, soft-delete. No image/video fields — the prompt's Food Library field list didn't include them (unlike Exercise, which does).

- **`DietPlanMeal`** — the Meal Builder: one row per food placed under a `mealType` slot (enum `BREAKFAST`/`MORNING_SNACK`/`LUNCH`/`EVENING_SNACK`/`DINNER`/`PRE_WORKOUT`/`POST_WORKOUT`). **Not tied to a day-of-week** the way `WorkoutPlanExercise` is tied to `dayOfWeek` — a diet plan's meals repeat every day of the plan (you eat breakfast daily, not just Mondays), so there's only one dimension (meal type) instead of two (day × slot). `sortOrder` orders foods within one meal type; `quantity` is a serving multiplier against the food's own base serving.

**Two endpoint groups, one shared service** — `FoodService` mirrors `ExerciseService` almost exactly (name uniqueness, soft-delete/restore bringing it back fully usable in one step). `DietPlanService` owns BOTH plan-catalog CRUD (create/update/activate/deactivate/soft-delete/restore/duplicate) AND the member-assignment/progress lifecycle (assign/remove/updateAssignment/getMemberDietPlans/updateProgress), same reasoning as `WorkoutPlanService`.

**Business rule: "only active trainers can create or assign diet plans"** — a private `assertTrainerActive()` on `DietPlanService`, a near-identical copy of Workout's version (tenant + non-deleted + holds `TRAINER` role + `status === 'ACTIVE'`). Kept as a separate copy rather than a shared helper — the two modules don't otherwise share code, and a shared util for one two-line check wasn't worth the cross-module coupling.

**Progress upsert — MERGE, not overwrite (the one real design departure from Workout Management)**: `DietPlanService#updateProgress` reads whatever daily log already exists for that `(assignmentId, date)` and merges the incoming fields against it — `waterIntakeMl`/`weightKg`/`notes` only overwrite when actually provided (omitted fields keep their previous value), and `mealsStatus` is a shallow-merged object (`{...existing, ...incoming}`), not a replacement. This matters because diet progress is naturally updated in several small separate calls across a day (log water in the morning, mark breakfast done after eating, log weight before bed) — unlike Workout's `MemberWorkoutProgress`, where each row is keyed by `(assignment, exercise)` so there's no merge question, diet's per-day row genuinely needs one call to not clobber another call's fields for the same day. **Duplicate** copies every plan field except a freshly-suffixed name (`"{name} (Copy)"`, incrementing on collision) AND copies the meal builder — always created `isActive: false`.

**Permissions**: `diets:view`, `diets:create`, `diets:update`, `diets:delete`, `diets:restore`, `diets:assign`, `diets:progress` — distinct from the pre-existing speculative `diet-plans:manage` (left seeded but unused, same precedent as every prior module). MANAGER gets all 7. TRAINER gets view/create/update/assign/progress (delete/restore stays Manager-only). RECEPTIONIST gets view only — identical grant shape to Workout Management, since the two modules have the same real-world access pattern (trainers/nutritionists run the day-to-day, front-desk just needs visibility).

## Finance Management (Prompt 19)

New `modules/finance/` — four routers (`member-payment.routes.ts` at `/payments`, `member-invoice.routes.ts` at `/invoices`, `income.routes.ts` at `/income`, `expense.routes.ts` at `/expenses`, `finance-dashboard.routes.ts` at `/finance`), same routes→controller→service→repository shape as every other module. Six new tables, RLS'd via a hand-written migration (`20260725071300_enable_rls_finance_management`, right after the model migration `20260725071154_finance_management_module`).

**Naming — a deliberate collision-avoidance**: this module's models are `MemberPayment`, `MemberInvoice`, `MemberInvoiceItem`, `MemberPaymentRefund` — **not** bare `Payment`/`Invoice`, which are already Prisma model names from Prompt 8 (FitCloud billing THE TENANT for its own subscription — `payments`/`invoices` tables, mounted at the SINGULAR `/payment`/`/invoice` routes). This module's routes are mounted at the PLURAL `/payments`/`/invoices` deliberately to avoid any path collision too. `MemberPaymentMethod` similarly avoids colliding with the pre-existing `PaymentMethod` **model** (a saved payment method for the tenant's own subscription, not an enum). These are genuinely separate concerns with zero shared code — gym-operations finance (charging members) vs. platform billing (FitCloud charging the tenant).

**Models**: `MemberInvoice` (invoiceNumber unique per tenant, member/branch, invoiceDate/dueDate, subtotal/taxAmount/discountAmount/totalAmount, `MemberInvoiceStatus` UNPAID/PAID/PARTIALLY_PAID/OVERDUE/CANCELLED) + `MemberInvoiceItem` (line items, quantity×unitPrice=amount). `MemberPayment` (paymentNumber unique per tenant, member/membership?/invoice?/branch, amount/discount/tax/finalAmount, `MemberPaymentMethod` CASH/UPI/CREDIT_CARD/DEBIT_CARD/BANK_TRANSFER/CHEQUE/ONLINE_GATEWAY — the last not wired to a real gateway yet, same "ship the enum value now" precedent as Attendance's device methods — `MemberPaymentStatus` PENDING/SUCCESS/FAILED/CANCELLED/REFUNDED/PARTIALLY_REFUNDED). `MemberPaymentRefund` (always a NEW row per refund, "refunds must create financial history" — a payment can have multiple partial refunds before reaching `REFUNDED`). `Income` (`IncomeCategory` MEMBERSHIP_FEE/PERSONAL_TRAINING/PRODUCT_SALES/OTHER, `sourcePaymentId` unique nullable — set only for auto-generated rows). `Expense` (`ExpenseCategory` RENT/SALARY/UTILITIES/EQUIPMENT/MAINTENANCE/MARKETING/OFFICE_SUPPLIES/OTHER, `receiptFileName`/`receiptDataUrl` — same no-object-storage data-URL convention as `MemberDocument`, same size cap/regex as `member.validators.ts#uploadMemberDocumentSchema` reused verbatim in `finance.validators.ts`).

**Two invoice-creation paths, one shared code path**: `MemberInvoiceService#generate()` is the manual "Generate Invoice" action (e.g. billing an upcoming renewal in advance — status `UNPAID`). `MemberInvoiceService#generateForPayment()` is called ONLY internally by `MemberPaymentService` the moment a payment succeeds with no `invoiceId` already attached (business rule: "every successful membership payment automatically generates an invoice" — status `PAID` since the settling payment already exists). Both funnel through a private `createInvoiceRow()` that reads `TenantInvoiceSettings` (Prompt 12 — `invoicePrefix`/`defaultPaymentTermsDays`) for the number prefix and default due-date window.

**Business rule: "prevent duplicate payments for the same invoice"** — if `MemberPayment.invoiceId` is supplied at creation, `MemberPaymentRepository#findActiveByInvoice` checks whether any non-cancelled/non-failed payment already settles that invoice, rejecting with `409` if so. If `invoiceId` is omitted and the payment succeeds, a brand new invoice is generated for it instead (see above) — so the two rules compose: pre-existing invoices can only ever be settled once, but a payment with no invoice never collides with anything.

**Auto-income, keeping the revenue ledger honest**: on every successful payment, `MemberPaymentService#onPaymentSucceeded` also creates one `Income` row (category `MEMBERSHIP_FEE`, `sourcePaymentId` = the payment's id, guarded by a DB-level `@unique` so it can never be duplicated even if the code path runs twice). `IncomeService#update`/`#softDelete` explicitly reject any income row that has a `sourcePaymentId` — auto-generated rows can only change by the payment itself changing (e.g. a refund does NOT currently reverse the income row — a deliberate scope limit, not a bug: refunds are their own financial-history trail via `MemberPaymentRefund`, and the dashboard's "Outstanding Payments" widget is invoice-status-based, not income-based).

**Refund mechanics**: `MemberPaymentService#refund` computes `remaining = finalAmount - sum(existing refunds)`, defaults the refund amount to the full remaining balance when not specified, validates `0 < amount <= remaining`, inserts a new `MemberPaymentRefund` row, and sets the payment's status to `REFUNDED` (fully covered) or `PARTIALLY_REFUNDED` (still has remaining balance) — never mutates `amount`/`finalAmount` on the original payment.

**"Verify Payment Status"** (`POST /payments/:id/verify`) is an authoritative read of the stored status for CASH/UPI/etc — nothing to poll. For a `PENDING` `ONLINE_GATEWAY` payment it now does real work — see §Razorpay Online Payments below; this was originally the documented seam for that integration, and Prompt 25 is what filled it in.

**First real PDF generation in this codebase** — `pdfkit` (pure-JS, no native binary, new dependency) renders `MemberInvoiceService#renderPdf` as an actual binary PDF for `GET /invoices/:id/download`. This is a deliberate departure from the Prompt-8 platform invoice module's `renderDownload()`, which ships HTML-only specifically because *"no rendering engine (puppeteer/pdfkit) exists in this codebase... swapping one in only touches this one method"* — this prompt's spec explicitly asked for "(PDF)" for member-facing invoices, so that swap-in happened here (the platform module is untouched and still HTML-only; the two are unrelated documents). "Email Invoice" reuses the existing `enqueueEmail` queue verbatim — since `EmailJobData` has no attachment support anywhere in the mail infra, it sends an HTML summary (invoice number/date/amount/status) rather than the PDF itself, not a real attachment.

**Permissions**: `finance:view`, `finance:payment-create`, `finance:payment-refund`, `finance:invoice-view`, `finance:invoice-download`, `finance:income-manage`, `finance:expense-manage` — distinct from the pre-existing speculative `payments:create`/`payments:read`/`payments:refund` (left seeded but unused, same precedent as every prior module) and distinct from `reports:view-financial` (which stays the gate for a future Reports module, not day-to-day finance ops). MANAGER gets all 7. RECEPTIONIST gets view/payment-create/invoice-view/invoice-download — front-desk records payments and views/downloads invoices; refunds and income/expense ledger management stay Manager-only (same tightening pattern as every prior module). TRAINER gets none — finance genuinely isn't part of a trainer's job in this design, the first module where a staff role gets zero grants.

**Verified live**: full API vitest suite 180/180 (including new `finance.validators.spec.ts`, 28 tests); live curl covering the full payment→auto-invoice→auto-income chain, the duplicate-payment-for-an-already-settled-invoice rejection, partial-then-full refund (confirmed refund history accumulates correctly and a fully-refunded payment can't be refunded again), a real PDF download (confirmed via `file` — `PDF document, version 1.3`, not HTML), a `PENDING`-status payment correctly skipping both auto-invoice and auto-income until it later succeeds, an auto-generated income row correctly rejecting direct edits/deletes, and the dashboard summary's today/monthly income, monthly expenses, and outstanding-payments numbers cross-checked against the exact payments/income/expenses created during the test run; plus a full Playwright E2E (record payment→verify status→follow the auto-generated invoice link→refund→generate a manual invoice→download its PDF→add manual income→create an expense→dashboard/members/workout-plans/diet-plans/attendance regression) — zero console errors.

## Razorpay Online Payments (Prompt 25)

Real Razorpay integration for Member Payments' `ONLINE_GATEWAY` method (Prompt 19 shipped the enum value but left it unwired — "ship the enum value now, wire the integration later," same precedent as Attendance's device methods). Deliberately separate from the platform Billing module's `PaymentGatewayPort` (Prompt 8) — that's a sandboxed Stripe/Razorpay/PayPal stub charging TENANTS for their own FitCloud subscription; this charges MEMBERS on behalf of the gym. Different money movement, different credentials (`RAZORPAY_KEY_ID`/`RAZORPAY_KEY_SECRET` in `env.razorpay`, same `isConfigured`-getter pattern as `env.pusher`), no shared code.

**Payment Links, not Orders/Checkout — a deliberate, corrected design choice**: the first pass of this work used Razorpay's Orders API plus the client-side Checkout widget (staff would open a card-entry modal and complete the charge themselves). That was explicitly rejected mid-build: **staff must never see or handle a card-entry UI**. The only two ways a gym-staff user can collect an online payment are (1) generate a Payment Link and send it to the member, who pays on Razorpay's own hosted page, or (2) mark it paid manually (CASH/UPI/etc — completely unchanged). `services/razorpay-gateway.service.ts` wraps only `paymentLink.create`/`paymentLink.fetch` from the `razorpay` npm SDK — there is no Orders-API call anywhere in this path, and no `checkout.js` script is ever loaded.

**`POST /payments/razorpay/link`** (`MemberPaymentController#createPaymentLink` → `MemberPaymentService#createPaymentLink`) validates the member/membership/invoice exactly like `create()`, requires the member to have an email or phone on file (`ValidationError` otherwise — Razorpay needs at least one to notify them), creates the `MemberPayment` row up front as `PENDING`/`method: ONLINE_GATEWAY` (so an unpaid link still shows up in the payment list, not silently lost), then calls `createPaymentLink()` with the computed `finalAmount` (in the currency's smallest unit) and the member's name/email/phone as the Razorpay `customer`. The Payment Link's `id` is stored in `transactionReference`; the response is `{ payment, shortUrl, paymentLinkId }` — no key ID, no client secret, nothing for a frontend widget to consume.

**Confirmation is a manual poll, not a webhook** — there's no public webhook URL in local dev. `MemberPaymentService#verifyStatus` (backing `POST /payments/:id/verify`, permission bumped from `finance:view` to `finance:payment-create` since it can now mutate) is a no-op passthrough for every payment EXCEPT a `PENDING` `ONLINE_GATEWAY` one with a stored `transactionReference`: for that case it calls `fetchPaymentLink(transactionReference)` and inspects Razorpay's own `status` field (`created`/`partially_paid`/`expired`/`cancelled`/`paid`) — `paid` flips the payment to `SUCCESS` (storing the real `razorpay_payment_id` over the old Payment Link id) and runs it through the exact same `onPaymentSucceeded()` hook every other successful payment path uses (auto-invoice, auto-income, `notifyPaymentReceived`) — no duplicate business logic; `expired`/`cancelled` flips it to `FAILED` and fires `notifyPaymentFailed`; anything else (still `created`) just returns the current `PENDING` status unchanged. This is staff-initiated ("Check payment status" button), not a background sweep.

**Frontend**: `/payments/new`'s "Online" channel is now labeled "Send Payment Link" (a `Link2` icon — deliberately not a card icon). Submitting generates the link and shows a read-only short URL + Copy button + a "Check payment status" button in place of any payment widget; there is no `razorpay-checkout.ts`-style script-loader anywhere in this codebase anymore (the first-pass version was deleted). `useVerifyPaymentStatus` now invalidates `payments`/`invoices`/`finance` query keys on success, since it can genuinely change state instead of just reading it.

**Verified live** against Razorpay's real test-mode API (not a mock): created a genuine Payment Link for `dana.lee`'s tenant (member Jamie Rivera, `MEM-0001`) and got back a real `https://rzp.io/...` short URL and `plink_...` ID; confirmed `/verify` polls Razorpay and correctly returns `PENDING` for an unpaid link; confirmed the old Orders-API routes (`/razorpay/order`, `/razorpay/verify`) are gone. Full API vitest suite 233/233 (finance validators spec now 31 tests — the 5 Order/Checkout-signature tests were removed since that flow no longer exists).

**Notify-channel control + resend + status tracking (same-session follow-up)**: the first pass always let Razorpay auto-derive which channels to notify from whatever contact details existed on the member, with no staff control and no way to resend. `createPaymentLinkSchema`/`CreatePaymentLinkInput` gained optional `notifyEmail`/`notifySms` booleans (default to `Boolean(member.email)`/`Boolean(member.phone)` when omitted from the request) — `MemberPaymentService#createPaymentLink` now explicitly rejects requesting a channel the member has no matching contact detail for (`ValidationError`), and `razorpay-gateway.service.ts#createPaymentLink` takes `notifyEmail`/`notifySms` as required params rather than auto-computing `Boolean(customerEmail)`/`Boolean(customerContact)` internally. `PaymentLinkDto` now echoes `notifiedEmail`/`notifiedSms` back so the frontend can show what was actually requested. New `POST /payments/:id/razorpay/notify` (`resendPaymentLinkNotificationSchema`, body `{ medium: 'email' | 'sms' }`) wraps Razorpay's own `paymentLink.notifyBy` via a new `notifyPaymentLink()` gateway function — a staff-triggered resend of the SAME link (not a new one), validated the same way as `verifyStatus` (must be a `PENDING` `ONLINE_GATEWAY` payment with a stored link id, `ConflictError` otherwise). Verified live: created a link with `notifyEmail:true, notifySms:false` and got back matching `notifiedEmail`/`notifiedSms`; resent it successfully via both `/razorpay/notify` mediums against the real Razorpay API; confirmed an invalid `medium` 422s; confirmed a member missing a requested contact channel is rejected with a specific message. Full API vitest suite 237/237 (finance validators spec now 35 tests, +6 for the new notify-flag/resend schemas).

Expands `modules/branches/` from Prompt 10's read-only scaffold (`GET /branches` returning a plain unfiltered active-branch array — name/isDefault/isActive/timezone only) into full CRUD. `Branch` gained: `branchCode` (auto-generated e.g. "BR-0001", same `nextXCode`-with-retry pattern as `MembershipPlan.planCode`), contact fields (email/phone/whatsappNumber), address fields (addressLine1-2/city/state/country/postalCode), geo (latitude/longitude, `Decimal(9,6)`), `operatingHours` (Json — same `{monday: {open,close,closed}, ...}` shape as `TenantSettings.businessHours` from Prompt 12's Gym Settings module, one level down at the branch), `holidays` (Json array of `{date, label}` — a lightweight list, never queried/filtered on, so no child table was warranted), capacity/maxMembers/maxStaff/allowCheckIn/notes, and `deletedAt` (soft-delete — didn't exist on this model before). Name/code uniqueness via an app-level pre-check (friendly error) backed by the DB constraint. The default branch cannot be deactivated or deleted (`ConflictError`) — same principle as it not being deletable in the spec, extended to deactivation too since an inactive default branch would be a confusing state. A tenant must always keep at least one active branch — checked independently in both `deactivate()` and `softDelete()` (`countActive() <= 1` guard). `setDefault()` requires the target branch to already be active, then clears every other branch's `isDefault` flag before setting the new one (`clearDefault()` + `setDefault()`, sequential — not a batched `$transaction`, per this codebase's tenant-scoped-client rule that individual calls must stay separate). `restore()` brings a branch back both un-deleted AND active in one step, matching Membership Plans/Staff/Members' "restore = fully usable again" precedent, not just a bare `deletedAt: null`.

MANAGER gets all 6. ## Scheduler & Background Jobs (Prompt 34)

**Every background/cron job in this codebase goes through `modules/scheduler/` — never add a module-local `Queue`/`Worker`/`repeat` call again.** This absorbed the 4 that used to exist scattered across `subscription`/`reports`/`members`/`tenant-announcements` (all deleted); their tested business logic moved unchanged into `modules/scheduler/handlers/*.handlers.ts`.

- **Adding a new job type**: write a handler function (`(ctx: JobExecutionContext) => Promise<Record<string, unknown> | void>`, in the matching `handlers/<category>.handlers.ts` file) and add one entry to `constants/job-registry.ts`'s `JOB_REGISTRY` array (`name`, `category`, `cronPattern`, `timezone`, `priority`, `maxRetries`, `retryDelayMs`, `timeoutMs`, `handler`). That's it — `initScheduler()` (called once from `server.ts`'s bootstrap, alongside `startEmailWorker()`) upserts it into the `ScheduledJob` table and registers its BullMQ repeatable schedule automatically. `name` is the BullMQ job name too — must be globally unique across the whole registry.
- **6 categories = 6 queues** (`scheduler-membership/attendance/payment/notification/report/maintenance`, one `Queue`+`Worker` pair each, concurrency 2) — a job's `category` determines which queue it runs on, there is no per-job queue choice.
- **Persistence model**: `ScheduledJob` (one row per job TYPE — the mutable scheduling state: `status`/`isPaused`/`cronPattern`/`lastRunAt`/`lastStatus`/`nextRunAt`) and `JobExecution` (one row per actual run attempt — durable history, since every job uses `removeOnComplete/Fail` on the BullMQ side and would otherwise retain zero history). Both admin-plane, no RLS (same convention as `FeatureFlag`).
- **Execution wrapper** (`scheduler-engine.service.ts#executeJob`): every run — scheduled, manual (`triggerJob`), or retry (`retryFailedJob`) — goes through this one function. Redis `SET NX` lock (`scheduler-lock:{jobName}`) guards against duplicate concurrent execution (belt-and-suspenders on top of BullMQ's own per-queue processing), the handler races against `timeoutMs` via `Promise.race`, and a thrown error is re-thrown after being recorded so BullMQ's own `attempts`/`backoff:{type:'exponential', delay: retryDelayMs}` drives the actual retry (each retry attempt = its own `JobExecution` row, via `bullJob.attemptsMade`).
- **Job actions**: `pauseJob`/`resumeJob` toggle `isPaused` and add/remove the BullMQ repeatable registration; `cancelJob` is pause PLUS purging any already-queued (not yet started) instances of that job name — `resumeJob` reactivates from either `PAUSED` or `CANCELLED`. `nextRunAt` is refreshed from BullMQ's own repeatable-job `next` field both on registration and after every execution — don't hand-compute it.
- **Queue actions**: `clearQueue` is `queue.drain(true)` (waiting/delayed backlog only) — deliberately NOT `obliterate()`, since failed/completed history must survive for the DB-backed history/failed-jobs endpoints (which read `JobExecution`, not BullMQ's own `getFailed()`/`getCompleted()`).
- **Permissions**: `scheduler:view`/`scheduler:manage`/`scheduler:trigger`/`scheduler:retry`/`scheduler:pause` (colon-separated, same convention as every other admin permission) — granted to `SUPER_ADMIN` (`*`) and explicitly to `TECHNICAL_ADMIN`. Routes: `/admin/scheduler/{dashboard,jobs,jobs/history,jobs/failed,jobs/:name,jobs/:name/{trigger,retry,pause,resume,cancel},queues,queues/:queueName/{retry,clear,pause,resume}}`.
- **Migrating an existing sweep INTO the registry** (if you ever need to do this again): extract the handler's pure business logic into `handlers/`, delete the old file's `Queue`/`Worker`/`startX/stopX` exports entirely, remove its start/stop calls from `server.ts`, add one `JOB_REGISTRY` entry. Don't try to force a well-tested multi-phase sweep (like the old `subscription-billing.jobs.ts`'s 7-phase lifecycle) apart into artificial separate "job types" just to match a spec's naming — keep it as one atomic handler if its phases were tested together, per CLAUDE.md's "extend, never redesign."

## AI Business Assistant (Prompt 35)

**Provider is fully swappable via env vars — `AI_PROVIDER`/`AI_MODEL`/`AI_API_KEY`/`AI_BASE_URL`/`AI_TEMPERATURE`/`AI_MAX_TOKENS` in `config/env.ts`'s `env.ai`. Never hardcode a provider or key anywhere in this module.**

- **Adding a new provider**: implement `AiProvider` (`providers/types.ts` — just `complete()` and `stream()`, the latter an `AsyncGenerator<string>` of text deltas) in a new `providers/<name>.provider.ts`, add one `case` to `providers/factory.ts`'s `getAiProvider()` switch. `openai-compatible.provider.ts` already covers any provider that speaks the OpenAI Chat Completions wire format — OpenRouter (default), OpenAI, Azure OpenAI (via its `buildUrl`/`authHeader` override params), and a local Ollama daemon all reuse it as-is; only genuinely different wire formats (Anthropic, Gemini) need their own adapter file.
- **`env.ai.isConfigured`**: `true` for `ollama` unconditionally, otherwise requires `AI_API_KEY`. Checked in TWO places — `factory.ts#getAiProvider()` (throws a 503 `AppError` if called anyway) and, more importantly, at the very top of `AiChatService#respond()` BEFORE anything is persisted. Don't remove that second check — without it, sending a message while unconfigured still persists the user's message (only the assistant reply fails), leaving an orphaned message with no reply once a key is later added; this was a real bug found via live testing, not a hypothetical.
- **Persistence**: `AiConversation` (per-user, RLS'd), `AiMessage` (`role` USER/ASSISTANT/SYSTEM; `actionPayload`/`actionStatus` populated only while a proposed action is `PENDING`), `AiRequestLog` (one row per actual provider call — separate from `AiMessage` since a request can fail before any message is created). All 3 tables tenant-scoped WITH RLS (this module's tables are NOT an admin-plane exception like the Scheduler's).
- **Context injection** (`services/ai-context.service.ts`): every section of the "what does this gym look like" system-prompt block is gated behind the SAME permission key its equivalent page already requires (`members:view`, `finance:view`, `reports:view`, etc.) — when adding a new context section, gate it the same way. Never add a section that ignores the calling user's permissions.
- **AI Actions are proposed, never auto-executed**: the model ends a message with a fenced ` ```ai-action ` JSON block (see `constants/system-prompt.ts` for the exact instructed format); `constants/action-types.ts#extractActionProposal()` parses + zod-validates it (malformed → silently treated as no action, never surfaced as an error) and strips it from the displayed text. The parsed proposal is persisted as `actionStatus: 'PENDING'` — nothing runs. Only `POST .../actions/:messageId/confirm` (→ `services/ai-actions.service.ts#executeAiAction()`) calls the real service, and only after re-checking the confirming user's permission for `ACTION_PERMISSIONS[type]` — the SAME real domain permission (`members:create`, `memberships:renew`, `workouts:assign`, `diets:assign`, `reports:export`, `notifications:manage`) the equivalent manual UI action already requires, not a separate blanket "AI actions" permission. **If you add a 7th action type, add its zod params schema AND its required permission to `ACTION_PERMISSIONS` in the same commit — a new action with no permission entry would be uncheckable, which `executeAiAction` doesn't currently guard against defensively.**
- **Streaming**: `POST /ai/conversations/:id/messages/stream` is this codebase's first raw SSE endpoint (`res.writeHead(200,{'Content-Type':'text/event-stream',...})`) — no prior precedent to follow if you add another. The controller ties an `AbortController` to `req.on('close')` and threads its `signal` all the way into the provider's `fetch()` call, so a client disconnecting (Stop Generation) actually cancels the upstream LLM call instead of just ignoring the response.
- **Permission**: `ai:use` (colon-separated) gates the whole module at the router level — granted to OWNER (`*`)/MANAGER/TRAINER/RECEPTIONIST, deliberately NOT MEMBER (this is a staff tool). Also gated behind the `ai_coach` tenant plan-feature-flag (Professional+ tiers) — an existing tenant provisioned before this flip needs its `TenantModule` row backfilled manually (re-seeding `prisma/seed.ts` only affects NEW tenant provisioning, never retroactively).
- **Gotcha confirmed live: OpenRouter's free-model lineup rotates** — the model `AI_MODEL` defaults to is whatever was confirmed working most recently (currently `inclusionai/ling-3.0-flash:free`; the ORIGINAL default, `meta-llama/llama-3.1-8b-instruct:free`, 404'd with "no longer available for free" the first time this was tested against a real key). If chat requests start failing with a 404/`AI_BASE_URL`-style error, check the current free list at `https://openrouter.ai/models?max_price=0` before assuming it's a code bug. Also avoid "reasoning" models (e.g. `openai/gpt-oss-20b:free`, `nvidia/nemotron-nano-9b-v2:free`) as the default — they stream their chain-of-thought into a separate `delta.reasoning` field (correctly ignored by `openai-compatible.provider.ts`, which only reads `delta.content`) and can burn the entire `max_tokens` budget on reasoning before ever emitting real `content`, making the assistant appear to return nothing.
- **Gotcha fixed live: use `||`, not `??`, when falling back to a computed default for an `optional()` env var.** `AI_BASE_URL=` (declared, empty) is a valid non-`undefined` string per zod — `env.ai.baseUrl ?? DEFAULT_BASE_URLS[provider]` never fell through to the default because `??` only triggers on `null`/`undefined`, not `''`. `factory.ts` uses `||` for exactly this reason. Any other optional env var merged against a computed fallback (not just passed straight through) needs the same `||`, not `??`.

- **Per-tenant BYOK (Prompt 35.5)**: `TenantAiSettings` (1:1 per tenant, every field nullable = "use the platform default for that field") lets a tenant override provider/model/key/baseUrl/temperature/maxTokens independently — `AiTenantSettingsService#resolveProviderOverride()` decrypts the stored key and hands back an `AiConfigOverride` that `getAiProvider(override)`/`getEffectiveAiConfig(override)` merge over `env.ai.*`. **Always resolve the override BEFORE persisting a user's chat message** (same discipline as the original not-configured guard) — a tenant's own bad key should fail the request cleanly, not leave an orphaned message. Every provider HTTP failure is classified into `AiErrorCode` (`providers/error-classification.ts`) via the response status and attached as `AppError`'s `details.code` — `ChatStreamEvent`'s error variant carries it through to the frontend so "your key is invalid" and "you're out of credit" render as actionable messages, not generic failures. `core/security/encryption.util.ts` (AES-256-GCM, `ENCRYPTION_KEY` env var) is this codebase's first real encryption-at-rest implementation — reuse it (don't invent a second scheme) for any future genuinely-secret tenant-supplied value.

- **Admin-side AI assistant (Prompt 35.6)**: `modules/admin-ai-assistant/` — the super-admin equivalent of the tenant AI assistant, query-only (no AI Actions). **Reuses `modules/ai-assistant/providers/*` directly** (the provider abstraction takes no tenant/admin-specific dependency, don't duplicate it if you touch this again). `PlatformAiSettings` is the admin-side "BYOK" table but application-enforced SINGLE-ROW (`PlatformAiSettingsRepository#find()` always returns the first/only row) — there's one platform team, not one row per admin user. Gated by the existing `dashboard:read` permission (not a new one) at the router level, `settings:manage` for the settings write endpoints — same reuse-don't-invent discipline as the tenant side's `ai:use`/`settings:manage` reuse.

## Member Self-Service Portal (Prompt 39)

**Third, fully independent JWT plane** — `core/security/member-jwt.service.ts` mirrors `admin-jwt.service.ts` exactly: same RSA keypair, audience `fitcloud-member-app` (`env.jwt.memberAudience`), claims `{sub: memberId, tenantId, sid, jti}`. **No `role`/`permVer` — the member plane has zero RBAC by design.** `req.memberAuth` is a third independent request property alongside `req.auth` (tenant staff) and `req.admin` (super admin) — never mix them, and never gate a `/portal/*` route with `requirePermission` (there's nothing to check against).

- **Login is by `memberId` (e.g. `MEM-0007`), never email.** `Member.email` is optional and has no `@@unique([tenantId, email])` — `memberId` does (`@@unique([tenantId, memberId])`), so it's the only field that can reliably identify one member.
- **Activation is staff-initiated, not self-registration.** `MemberService#sendPortalInvite(id, actor)` (gated `members:update` — no new permission minted) creates the `MemberCredential` row (`PENDING_ACTIVATION`) + a `MemberVerification` row + emails an activation link via `memberPortalInviteEmail`. `modules/member-auth/services/member-auth.service.ts#createOrResendInvite` is idempotent — calling it again on an already-`PENDING_ACTIVATION` member resends rather than erroring, `ACTIVE` members are rejected.
- **`MemberVerification` is dual-purpose** (`purpose: ACTIVATION|PASSWORD_RESET`, same table) — same "reuse one opaque-token table for two flows" pattern the staff activation flow already used with `PasswordReset`.
- **`modules/member-portal/` routes are deliberately dumb**: every method takes `memberId` from `req.memberAuth.sub` (never a caller-supplied param) and filters every query to it — that IS the authorization, there's no second check. RLS isolates by `tenant_id`, not by member-within-tenant, so this application-level filtering is load-bearing, same pattern branch-scoping already relies on elsewhere in this codebase.
- **Reuses existing services' logic, doesn't reimplement it**: `markWorkoutProgress`/`logDiet` call straight into `MemberWorkoutPlanRepository`/`MemberDietPlanRepository`'s existing merge-not-overwrite methods — a partial diet log (e.g. just today's water) must not wipe an already-logged meal for the same day, and that logic already existed for the staff-side flow.
- **No Redis denylist on member sessions** (unlike the tenant plane) — a documented deliberate simplification in `member-authenticate.middleware.ts`; logout relies on refresh-token revocation only. Revisit if member-portal logout-everywhere ever becomes a real requirement.
- **Audit**: `AuditLog.actorUserId: null, actorRole: 'MEMBER'` for every member-initiated write (both columns already nullable/free-text, no schema change needed).

## Class/Session Booking (Prompt 39)

`modules/classes/` — `GroupClass` (the recurring definition) → `GroupClassSchedule` (weekly template, `dayOfWeek`+`startTime` "HH:mm") → `ClassSession` (a dated, concrete, bookable occurrence, generated FROM the schedule) → `ClassBooking` (one member's seat in one session). - **Session generation is idempotent by construction**: `ClassSessionService#generateUpcomingSessions(daysAhead=28)` checks `findExisting()` before every insert, backed by `@@unique([groupClassId, sessionDate, startTime])` as a schema-level safety net — calling it twice in a row is always a safe no-op the second time. - **Adding a new `JobCategory`**: it's a native Postgres enum backing `ScheduledJob.category` — adding one (like `CLASS` here) needs its own `ALTER TYPE ... ADD VALUE` migration (`prisma migrate dev` generates this correctly), PLUS updating `JOB_CATEGORIES` in `modules/scheduler/validators/admin-scheduler.validators.ts` (a hand-maintained zod enum, not derived from the Prisma enum). `queueNameForCategory()`/`scheduler-engine.service.ts` need NO changes — queue setup is fully registry-driven from `JOB_REGISTRY`, this is confirmed by inspection, not assumed.
- **One `book()` method for both booking paths**: `ClassBookingService#book(sessionId, memberId, actor: {role: 'STAFF'|'MEMBER', userId?})` is called identically from the staff controller (`POST /bookings`) and `MemberPortalService#bookClass` (`POST /portal/classes/:id/book`) — this is why a staff booking and a member self-booking count toward the exact same `capacity` number without any special-casing. Eligibility mirrors `AttendanceService`'s own check (active, non-frozen membership, active non-expired `Membership` row).
- **Capacity is count-then-insert, not a locked transaction** — see the "Known dev-only caveats" entry in PROJECT-STATE.md. Don't "fix" this with a `SELECT ... FOR UPDATE` or advisory lock unless a real overbooking incident happens; it's a deliberate, documented tradeoff for a low-frequency write path.
- **`@@unique([classSessionId, memberId])` is permanent, not just "while active"** — a member can only ever have ONE `ClassBooking` row per session, full stop. This means cancelling and then rebooking the SAME session is not a fresh insert — `ClassBookingRepository#upsertBooking()` (not `create()`) MUST be used in `book()`, reviving the existing cancelled row back to `BOOKED` instead. **If you ever add a second write path that creates a `ClassBooking` row directly, it must also go through `upsertBooking`, or rebooking after a cancel will throw a raw unhandled Prisma P2002 (surfaces as a 500)** — this exact bug shipped once during this prompt's own Playwright verification and was caught by the test driving a real cancel→rebook cycle through the UI, not by curl (which only exercised book-then-cancel, never rebook).
- **New route files need `router.use(authenticateMiddleware)` explicitly** — it is NOT applied globally; every existing module's routes file (e.g. `branch.routes.ts`) has this line near the top, and it was missed on all three of this module's route files initially, producing a bare "Authentication required" 401 despite `requirePermission` being present on every route (permission checks run AFTER authentication and never even executed). Static checks (typecheck/lint/build/vitest) cannot catch a missing middleware registration — only live request testing does.
- **Permissions**: `classes:view/create/update/delete/restore` + `bookings:manage` (MANAGER: all 6; TRAINER: `classes:view` only; RECEPTIONIST: `classes:view`+`bookings:manage` — front-desk booking is receptionist-tier work, same as their existing attendance/payment-create permissions). Feature-gated behind the plan-feature-flag catalog key `live_classes` (relabeled from its pre-existing "coming soon" placeholder — see PROJECT-STATE.md Prompt 39 entry — not a new key).

## Mandatory Two-Factor Authentication (Prompt 42)

Before this prompt, `User.mfaEnabled`/`mfaSecret` were dead columns — nothing ever wrote to them, and `/two-factor`'s "enter the code from your authenticator app" copy was aspirational (the backend actually emailed a 6-digit code). This prompt built REAL TOTP and a tenant-wide policy for requiring it on specific staff roles.

- **`core/security/totp.util.ts`** wraps `otplib@13`, whose API is a full break from the classic `authenticator` singleton some training data remembers — it exports standalone functions, not a namespace object: `generateSecret()`/`generateURI()` (sync) and `generate`/`verify`/`generateSync`/`verifySync` (the latter two sync, `verifySync` returns `{valid, delta, ...}` not a plain boolean). Confirmed via `node -e "console.log(Object.keys(require('otplib')))"` — check this again before touching TOTP code if it's ever upgraded. Secrets are encrypted at rest with the EXISTING `core/security/encryption.util.ts` (AES-256-GCM, originally built for tenant AI API keys, Prompt 35.5) — don't invent a second encryption scheme.
- **Policy lives on `TenantSettings.mfaRequiredRoles: Json`** (array of role name strings, e.g. `["OWNER","MANAGER"]`), NOT a boolean column on `Role` — system roles (OWNER/MANAGER/TRAINER/RECEPTIONIST) are immutable in this codebase's IAM model (clone-to-edit only, see §Authorization above), so a per-role boolean would require cloning a system role just to flag it. `AuthService#login` checks the user's role names (`roleRepository.getRoleNamesForUser`) against this list after password verification.
- **Grace-token pattern for forced setup**: a user whose role newly requires 2FA but hasn't set it up yet gets a `mfa_setup_required` challenge (not a hard block) carrying a short-lived `MfaSetupToken` (15 min, hash-and-expire shape identical to `PasswordReset`) — this proves the password was already correct without granting a real session, and is scoped only to `/auth/mfa/setup/*`. Completing setup with a real code (`completeMandatorySetup`) both enables 2FA AND finishes login in the same request — the user doesn't log in twice.
- **One setup/confirm engine, two entry points**: `AuthService#beginTwoFactorSetup`/`confirmTwoFactorSetup` are the actual implementation (generate secret → store encrypted, not yet enabled → verify first real code → flip `mfaEnabled` → issue + store 10 hashed backup codes, returned once in plaintext). Both the mandatory grace flow (`beginMandatorySetup`/`completeMandatorySetup`, resolves `userId` from the setup token) and the self-service profile endpoints (`modules/profile/`, resolves `userId` from `req.auth.sub`) call these same two methods — don't duplicate the TOTP/backup-code logic a second time for either entry point.
- **Login-time verification handles TOTP and backup codes with one method**: `verifyTwoFactorCode` tries a real TOTP code first, falls back to `mfaRepository.consumeBackupCodeIfValid(hashToken(normalizeBackupCode(code)))` — backup codes are single-use, consumed atomically on match. `resendOtp` for `purpose: '2fa'` is now a documented no-op — there's nothing to resend for a TOTP code.
- **Self-service** (`modules/profile/`, `POST /profile/two-factor/{setup,setup/confirm,disable,backup-codes/regenerate}`): `disableTwoFactor` requires re-entering the current password; `regenerateBackupCodes` requires a current TOTP code. Both are security-sensitive enough to re-verify rather than trust the bearer token alone.
- **Admin policy endpoint**: `GET/PATCH /settings/security` (existing `settings:read`/`settings:manage` permissions — no new permission key minted) manages `TenantSettings.mfaRequiredRoles`.
- **New tables, both RLS'd**: `MfaBackupCode` (hashed, one-time-use, `@@index([userId])`) and `MfaSetupToken` (mirrors `PasswordReset`'s shape exactly).

## Field-Level Encryption for Member PII (Prompt 43)

`Member.email`/`Member.phone` are AES-256-GCM ciphertext at rest (`core/security/encryption.util.ts` — the same scheme as `TenantAiSettings.apiKeyEncrypted`/`User.mfaSecret`), with a parallel `emailHash`/`phoneHash` column (`core/security/blind-index.util.ts`, deterministic HMAC-SHA256, subkey derived from `ENCRYPTION_KEY`) for exact-match lookups — GCM's random IV makes ciphertext non-deterministic, so it can't be equality- or `contains`-matched in SQL.

- **Single write funnel, decrypt-at-repository-boundary for reads within `members`**: `MemberRepository#create`/`update` encrypt+hash via `modules/members/utils/member-pii.util.ts#encryptContact` (nothing else writes to the `members` table). `MemberRepository`'s own reads (`list`/`findDetail`/`findByQrToken`/`listForExport`) decrypt before returning — `member.service.ts` and everything downstream (DTOs, CSV export) needed zero changes.
- **Every OTHER read site must decrypt explicitly** — any `db.member.findFirst(...)` outside `member.repository.ts`, or a relational `include: { member: true }` on a different model (`MemberInvoice`/`MemberPayment`/`Membership`), returns ciphertext in `.email`/`.phone` until you call `decryptMemberContact`/`decryptMemberContactMany`/`decryptMemberContactNullable` (`member-pii.util.ts`) on the result. Current call sites doing this: `finance/services/member-payment.service.ts`, `member-invoice.service.ts`, `member-auth/services/member-auth.service.ts` (portal login + forgot-password), and the cross-tenant scheduler jobs in `scheduler/handlers/{payment,membership,notification}.handlers.ts` (these use the RAW `prisma` client, not a tenant-scoped one, since they sweep every tenant). **If you add a new place that fetches a `Member` row and touches `.email`/`.phone`, it needs this too — nothing enforces it automatically.**
- **`findByEmail`/`findByPhone` (uniqueness checks) query by hash, not plaintext** — `hashEmail`/`hashPhone` normalize (lowercase+trim for email, trim for phone) before hashing, matching the normalization already applied at encryption time, so a differently-cased/whitespaced duplicate is still caught.
- **The member-list free-text search lost partial email/phone matching** — `MemberRepository`'s `buildWhere` no longer includes `email`/`phone` in its `contains` OR clause (ciphertext can't be substring-matched); only name/Member ID search remains. An EXACT email/phone still resolves via `findByEmail`/`findByPhone`'s hash lookup. This was a deliberate, user-confirmed trade-off, not an oversight — don't try to restore partial matching without discussing the alternative (decrypt-and-filter in memory, which doesn't scale).
- **A Prisma Client Extension (transparent encrypt/decrypt on every Member query) was considered and rejected** — composing it with the existing tenant-scoping RLS extension's `$transaction`-based `set_config` pattern (`tenant-scoped-client.ts`) raised correctness questions about extension-chain ordering that weren't worth the risk; this codebase's established style is explicit funnels anyway (see how `mfaSecret`/`apiKeyEncrypted` are handled — no Prisma middleware there either).
- **One-off data migration**: `apps/api/scripts/backfill-member-pii.ts` (run via `pnpm --filter api exec tsx scripts/backfill-member-pii.ts`) encrypts any pre-existing plaintext row — idempotent, only touches rows where the hash column is still NULL.

## Global Search (Prompt 44)

`modules/search/` — `GET /search?q=` (authenticated only, no `requirePermission` gate — see why below). Scoped to Members, Staff, and Branches only (the "look someone/somewhere up by name" entities); other modules' own list-search stays in-page.

- **Reuses each module's existing repository `list()` method** (`MemberRepository`/`StaffRepository`/`BranchRepository`) with the incoming query as that method's own `search` param, capped to `limit: 5` — no separate query logic. A result here always matches what that module's own list page would find, by construction, not by keeping two implementations in sync.
- **Permission-filtered per category, not gated by `requirePermission`** — that middleware only expresses a single required key, and this route spans three independently-permissioned entity types. `GlobalSearchService#search` calls `permissionEngine.getEffectivePermissions(tenantId, userId)` once (already Redis-cached) and only queries a category if `members:view`/`staff:view`/`branches:view` is present — a category the caller can't see is silently omitted, never a 403. **If you add a 4th searchable entity, follow this same pattern** — don't add a second `requirePermission`-gated route; extend the permission check inside the service.
- **`q` must be ≥1 char at the validator (422 otherwise) but the service treats <2 chars as an empty result** — avoids a single keystroke returning a noisy near-full-table response before the frontend's debounce settles.

## Health check (Prompt 45)

`GET /health` (mounted in `app.ts`, before `tenantMiddleware` — already in `PLATFORM_ONLY_PATHS`, no tenant needed) runs `core/health/health-check.util.ts#checkHealth()`: a real `SELECT 1` (raw `prisma`, since no tenant is known yet at this route) and a real `redis.ping()`, in parallel, each timed. `200 healthy`/`200 degraded` (Redis down only) / `503 unhealthy` (DB down). **If you add a new hard dependency the app can't run without (a new required external service), add its own check here** — don't let `/health` silently stay green while a real dependency is down, which is exactly the gap this replaced (the old version was a pure `{status:'ok'}` liveness no-op that would have stayed 200 through a real Postgres outage).

## GDPR Export/Erasure for Members (Prompt 46)

`modules/members/services/member-gdpr.service.ts` — standalone service (not folded into `MemberService`), called identically from the staff-side `GET /members/:id/gdpr-export`/`POST /members/:id/gdpr-erase` (`modules/members/routes/member.routes.ts`) and the member-portal's own `GET /portal/gdpr-export` (`modules/member-portal/`), same "one core engine, two entry points" shape as mandatory 2FA.

- **`exportData`**: aggregates profile (via `MemberRepository#findDetail`, already decrypted per Prompt 43) + attendance + workout/diet plan assignments (progress/log entries as COUNTS, not full detail) + invoices + payments + document metadata (not file contents) + class bookings, all queried directly against the tenant-scoped client (not through each owning module's repository — those are shaped for their own UI, not a flat export).
- **`eraseData` ANONYMIZES, never hard-deletes**: overwrites name/contact/medical/emergency-contact fields on the `Member` row, hard-deletes `MemberCredential`/`MemberSession`/`MemberVerification` (portal access) and `MemberDocument` rows, soft-deletes the member. Financial rows (`MemberInvoice`/`MemberPayment`/`Membership`) are left in place on purpose — they have `onDelete: Restrict` FKs to `Member` (a hard delete would be blocked anyway) and typically need retention for accounting regardless of an erasure request; once the source `Member` row carries no PII, neither do they. Audit-logged as `member.gdpr_erased`.
- **New permission `members:erase-data`** (OWNER/MANAGER only, seeded — re-run `prisma:seed` if you don't see it) — irreversible, so it's gated at the same tier as `members:delete`/`restore`, not the broader `members:view`/`update` staff already have. **No self-service erasure** exists — only staff can trigger it, a deliberate choice to keep a human in the loop on an irreversible action (self-service EXPORT is fine and exists at `/portal/gdpr-export`).
- **Known gap**: `core/storage/storage.service.ts` has no delete-object capability at all (upload/presign only) — `eraseData` deletes the `MemberDocument` DB rows but the underlying object-storage files are orphaned. Wire real object deletion in here if that capability ever gets added.

## Password hashing (perf fix, Prompt 13.5)

`core/security/password.service.ts` is the one place to hash/verify passwords — use it, don't call a bcrypt-family lib directly (the only other direct call sites, `admin-roles` and `prisma/seed.ts`, exist because they can't import from `src/`). It wraps `@node-rs/bcrypt` (napi-rs, prebuilt binaries, no build step) at `env.security.bcryptSaltRounds` (default 10). This used to be `bcryptjs` (pure-JS) at cost 12, which made login/register/every password path take ~900ms — `bcryptjs` is gone from the repo entirely. The cost factor is embedded in each hash at creation time, so lowering the env default doesn't speed up existing hashes — only newly hashed passwords get the faster cost.
