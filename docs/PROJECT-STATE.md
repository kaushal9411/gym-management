## Dev commands

```bash
# from each app dir (pnpm may need `corepack pnpm` on this machine)
pnpm run dev            # api: tsx watch · web: next dev
pnpm exec tsc --noEmit -p tsconfig.json
pnpm exec eslint src --max-warnings=0
pnpm run build
pnpm exec vitest run    # api only; globs src/**/*.spec.ts
pnpm run prisma:seed    # api; idempotent upserts
pnpm exec prisma migrate dev --name <name> --skip-seed
```

Gotchas: killing dev servers can leave orphaned `node.exe` listeners — kill by port (`Get-NetTCPConnection -LocalPort 3001`). Running `next build` while `next dev` runs corrupts `.next` and kills the dev server. Env vars load once at API startup (restart after `.env` edits). After changing seed permissions, re-run seed AND consider Redis `FLUSHALL` for stale permission caches.

13.5 — **Password-hashing perf fix**: `/auth/login` (and every other password hash/verify path — register, staff activation, password reset) was measured live at ~900-950ms while every other endpoint ran 25-110ms. Root cause: `bcryptjs` (pure-JS bcrypt) doing a single `compare()` at cost factor 12 takes ~550-900ms on its own on dev hardware — confirmed by direct benchmark, not a DB/query issue. Fix: swapped the sole choke point `core/security/password.service.ts` (plus the two other direct-bcrypt call sites, `admin-roles/services/admin-role.service.ts` and `prisma/seed.ts`) from `bcryptjs` to `@node-rs/bcrypt` (napi-rs, prebuilt binaries for win32/darwin/linux — no node-gyp/build-tools step, same `$2` hash format so existing hashes keep verifying), **and** lowered `BCRYPT_SALT_ROUNDS` default from 12 → 10 (`.env`/`.env.example`/`config/env.ts` zod default; min allowed is still 10). Net: new hashes verify in ~260-280ms instead of ~950ms. Note the cost factor is baked into each stored hash at creation time — existing users keep their old (slower) hash until their password changes; the 4 documented dev test-credential accounts (`dana.lee`, `sam.staff`, `invited.trainer`, `admin@fitcloud.com`) were rehashed at cost 10 with their same known passwords so the fix is visible immediately, credentials unchanged. `bcryptjs`/`@types/bcryptjs` removed entirely (no remaining references). Verified: typecheck/eslint(0 warnings)/build/vitest(51 passed) all green, plus live curl timing before/after on the running dev stack.

45 — **Real DB/Redis-checking `/health` endpoint** (audit remediation, sixth Medium-priority item). `app.ts` already had a bare `GET /health` (mounted before `tenantMiddleware`, correctly platform-exempt) — but it was a pure liveness no-op (`{status:'ok', uptimeSeconds}`), never actually checking anything. Found and fixed live during this exact session: a genuine Docker restart left Postgres briefly unreachable, and the old `/health` would have reported `200 ok` the entire time — the precise failure mode this item exists to close.

New `core/health/health-check.util.ts#checkHealth()`: a real `SELECT 1` against Postgres (via the raw `prisma` client, not tenant-scoped — this route runs before any tenant is known) and a real `PING` against the shared `redis` (ioredis) client, run in parallel, each independently timed. Three-way status: `healthy` (both up), `degraded` (DB up, Redis down — sessions/rate-limiting/caching misbehave but most traffic still serves, so this stays **200**), `unhealthy` (DB down — nothing works without it, **503** so a load balancer/orchestrator actually stops routing traffic here). `sendError` (`core/http/response.ts`) gained an optional 5th `data` param (previously hardcoded `null`) specifically so the unhealthy response could still carry the full `checks` payload — a health check's failure response is exactly when the diagnostic detail matters most.

**Export** (`GET /members/:id/gdpr-export`, staff, `members:view`; `GET /portal/gdpr-export`, member self-service, own id only): a single bundle of everything genuinely personal — profile (decrypted email/phone + medical/emergency-contact fields), membership history, freeze history, attendance, workout/diet plan assignments (+ progress/log COUNTS, not the full per-entry detail — kept deliberately summary-level), invoices, payments, document metadata (type/filename/upload date, not file contents), and class bookings. Both entry points call the SAME `MemberGdprService#exportData` (new, standalone service, not folded into `MemberService`) — the "one core engine, two entry points" shape already established for mandatory 2FA.

**Erasure** (`POST /members/:id/gdpr-erase`, staff-only, new permission `members:erase-data` — granted to OWNER/MANAGER, deliberately NOT to TRAINER/RECEPTIONIST, matching how `members:delete`/`restore` are already Manager-tier-only; **no self-service erasure** — a member can't erase their own account, only request it through staff, a deliberate scope-narrowing to avoid a coerced/accidental-click irreversible action with no human review) **anonymizes rather than hard-deletes**: name/email/phone/DOB/address/medical/emergency-contact/notes fields on the `Member` row are overwritten (`firstName: 'Erased'`, contact fields `null`, `notes` replaced with an erasure marker), portal access is fully revoked (`MemberCredential`/`MemberSession`/`MemberVerification` rows hard-deleted), uploaded `MemberDocument` rows are hard-deleted, and the member is soft-deleted (`deletedAt` + `INACTIVE`). Financial rows (invoices/payments/memberships) are DELIBERATELY left in place — `onDelete: Restrict` FKs from `MemberInvoice`/`MemberPayment` to `Member` would block a hard delete anyway, and accounting/tax records typically need retention regardless of an erasure request; once the source `Member` row carries no identifying info, those rows carry none either. Every erasure is audit-logged (`member.gdpr_erased`).

**Known limitation, documented in code**: `MemberDocument` DB rows are deleted but the underlying object-storage files are NOT — `core/storage/storage.service.ts` has no delete-object capability anywhere in this codebase yet (upload/presign only). ## Known dev-only caveats (deliberate, documented in code)

- **RLS bypass in dev**: the app connects as a Postgres superuser, so raw-`prisma` (unscoped) queries bypass RLS. Production needs a non-superuser role. Every intentional cross-tenant raw query carries a comment saying so.
- **Pusher is an honest no-op stub** (no credentials configured); Socket.IO is the real realtime path.
- **Platform Billing gateways (Prompt 8, tenant-subscription charges) are sandboxed stubs** — provider pattern is real, nothing charges. **Member Payments' Razorpay integration (Prompt 25) is real** — genuine Payment Links API calls against Razorpay test-mode credentials; a Payment Link actually charges a real (test-mode) card/UPI/etc if someone pays it.
- **Uploads go through object storage when configured, else degrade to data-URLs** (Prompt 37 — `core/storage/`): avatars/member-photos/exercise-images/QR-codes/branding assets land under the bucket's public-read `public/` prefix as stable direct URLs; member documents and expense receipts (genuinely sensitive) land under `private/` as a bare object key, re-signed to a fresh 1h presigned URL on every read — never persisted as a permanent URL. Historical rows created before this migration keep their old base64 data-URL until their next write (no backfill was done).
- `user_roles` / `role_permissions` / `permissions` are global link/catalog tables **without RLS** — isolation enforced at service layer (roles carry `tenantId`, queries join through users).
- **Class booking capacity is count-then-insert, not a locked transaction** (Prompt 39 — `class-booking.service.ts`): a true concurrent race on the literal last seat could let two bookings both pass the check and both insert. Accepted for a low-frequency write path, documented in both the schema comment and the service — not solved with distributed locking.
