### How the phone receives flags
* `TenantBranding.featureFlags` (`models/tenant_branding.dart`) parses `featureFlags` (string array) from `GET /public/tenants/resolve`. Missing field => empty list (every flagged tile hidden). Live payload (kaushal-fitness-club, all enabled) = 23 keys: the 11 platform keys + `analytics, api_access, branches, chat, custom_domain, dashboard, email_templates, members, membership_plans, sms_templates, staff, white_label`. Disabling `diet_plans` (then `expenses`) removed exactly that key from the array (23 -> 22) and the restore brought it back; all flags were left enabled (lock protocol followed, held ~15 s).
* Other keys the Dart code references: only `staff`, `branches`, `membership_plans` (plan-only modules used by menu tiles). Nothing else; `members`/`chat`/`analytics` are never read.
* The ONLY consumers are `MenuEntry.featureFlag` (the 4 staff drawers: owner, manager, receptionist, trainer), `AttendanceAccess` (manager Attendance tab History shortcut) and `SupportAccess`. No shell/bottom-nav, dashboard, router, search, push-tap or member-plane code reads it.
* Refresh timing: the tenant is resolved in `SessionCubit.restore()` (cold start / maintenance exit) and at login (`staffSignedIn`/`memberSignedIn`). It is NOT re-read on app resume (`main.dart` resume only reloads platform config), not on pull-to-refresh, not periodically. A phone keeps the flags from its last cold start/login indefinitely. `refreshStaffUser()` re-emits with the OLD tenant. Also `SessionAuthenticatedStaff/Member.props = [user.id, tenant.slug]` omit the flags, so even a future re-emit with new flags would be dropped by Equatable.
* Error handling when an API 403s ("This module is currently unavailable."): `dio_client` passes 403 straight through (no logout, no retry); screens show it via `AppErrorView`/inline `FormAlert` with Retry. Verified by existing tests for expenses, income, reports hub, scheduled reports, AI settings, owner dashboard (per-section degrade), people reports. New finding: `MemberClassesScreen` uses a record `(a, b).wait`; when both requests fail it shows "Could not load classes (ParallelWaitError ...)" instead of the server message (graceful, no crash, ugly text).
* Staff menus are tile-gated by flag AND permission (`visibleMenuSections`). Hidden tiles = no entry point, but nothing blocks the routes: `app_router.dart` `redirect` only checks session state, so any `AppRoutes` path still opens (e.g. via links from other screens) and then fails on the API.
* Push tap (`PushNotificationService._navigateFor`): staff -> `/notifications`, member -> `/member/notifications`, HR types -> HR routes. No flag check; a cold-start tap just opens the app.

## API (apps/api) — audited 2026-11-22

### Flags and modules
DB `feature_flags` holds exactly the 11 seeded keys (no extras): `ai_coach`, `notifications`, `support_tickets` (communication); `expenses`, `income`, `payments` (finance); `reports` (insights); `attendance`, `diet_plans`, `live_classes`, `workout_plans` (operations). Tenant `kaushal-fitness-club` (Enterprise plan) has 25 `TenantModule` rows: the 11 above plus `members, staff, branches, membership_plans, dashboard, analytics, chat, email_templates, sms_templates, api_access, white_label, custom_domain` (all enabled) and `marketplace`, `video_training` (disabled). Keys with no `FeatureFlag` row read as platform-enabled.

### Mechanism
`ResolvedTenant.featureFlags = TenantModule(enabled) AND FeatureFlag.enabled` (`tenant.service.ts#toResolvedTenant`). Platform flags sit in a separate 30 s cache `platform:feature-flags:enabled`, busted by `AdminFeatureFlagService#setEnabled` (PATCH `/admin/feature-flags/:key`), so a toggle is live immediately (live-verified at t=0 and t=32 s). Server gate: `requireModuleEnabled(key)` (router-level, 27 staff routers) answers `403 "This module is currently unavailable."`. The same gate covers plan-disabled modules (live-verified via `PUT /admin/tenants/:id/modules/support_tickets`, restored). The older `requireFeature` in `authentication/middlewares/feature-access.middleware.ts` was unused dead code and has been DELETED (fix pass, see below).

#### Why membership changes still write finance rows (gap 5, intentional, unchanged)
Membership assign / renew / upgrade / transfer keep auto-creating the invoice, payment and income rows when the `payments` or `income` module is switched off. This is deliberate. Those rows are the *ledger*: the record of money (or an amount owed) the gym actually receives when it sells or changes a membership, and the member's balance, "no double payment" checks and membership price history are computed from them. The `payments`/`income` flags switch off the *features* (the Payments/Income screens, online payment links and checkout, reports of them), not the accounting of a sale. Skipping the rows when a flag is off would leave a sold membership with no invoice/income, silently corrupt balances, and make the data wrong the moment the module is re-enabled. So the module gate is only a UI/API-surface kill switch for the finance screens; the ledger is always written, and with the module off the rows are simply not viewable/editable until it returns.
